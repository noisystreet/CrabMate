# AGENTS.md

## Cursor / Trae specific instructions

### Project overview

CrabMate is a Rust-based AI Agent that calls **OpenAI-compatible** `chat/completions` backends (e.g. **DeepSeek**, **MiniMax**, **Zhipu GLM**, **Moonshot Kimi**, **Ollama**). It provides HTTP **`serve`** (Axum) and ops CLIs; **official Web UI / Desktop / remote terminal (`crabmate-tui`)** live in **[`crabmate-client`](https://github.com/noisystreet/crabmate-client)** (local sibling `../crabmate-client`; Playwright forwarding honors **`CRABMATE_CLIENT_DIR`**). In-process **`repl` / `chat` / `tui`** (clap entry **and** implementation) **are removed** (D2.2; see `docs/design/client_shell_split.md`). See `README.md` for quick start; `docs/配置说明.md` for env vars and TOML; `docs/命令行与路由.md` for subcommands and routes; `docs/工具说明.md` for built-in tools; `docs/开发文档.md` for architecture overview. If you change module layout or layering, update `docs/开发文档.md` per **Repository engineering rules → Architecture & documentation sync** below.

### Agent workspace

- Temporary documents, analysis reports, design drafts, and other non-code artifacts generated by the agent must be placed in the **`agent_space/`** directory.
- `agent_space/` is listed in `.gitignore` and will not be committed to the repository.
- This directory isolates intermediate agent outputs, keeping the project root and `docs/` clean.
- **Do not cite, link, or treat `agent_space/` files as project documentation.** Authoritative docs live under **`docs/`** (and root `README*` / `AGENTS.md`). When a draft matures, graduate it into `docs/` (or `docs/design/`) and point readers there—never leave lasting references to `agent_space/…` in committed docs, code comments, PR bodies, or agent replies that claim “see the plan at …”.

### GitHub Flow workflow

- Use **GitHub Flow** as the default delivery model: branch from `main` for each change, open a PR, and merge back to `main` after checks pass and review is done.
- Keep `main` always releasable: avoid direct pushes to `main` for feature work; prefer short-lived branches and small PRs.
- **Start from an Issue**: new plans, designs, and non-trivial refactors must have a tracking Issue first (`gh issue create`). The body states the problem, the intended scope, and the explicit non-goals, and cites the relevant `docs/` anchor. Trivial fixes (typo, one-line bug fix) may skip the Issue; a design draft stays in `agent_space/` until the Issue settles it, then graduates into `docs/design/`.
- **Link the PR to its Issue**: before merging, the PR body references the tracking Issue — `Closes #123` when the PR completes it, `Refs #123` when it only advances it (keep the Issue open in that case). Do not silently widen scope inside a PR; file a follow-up Issue instead.
- **Branch naming**: `type/short-slug`, where `type` is the commit type (`feat` / `fix` / `docs` / `refactor` / `test` / `perf` / `build` / `ci` / `chore`). Include the Issue number when one exists (`feat/842-ltm-hybrid-retrieval`). `main` is the only long-lived branch; delete the branch after merge.
- Before opening or merging PRs, run required local checks (at least `pre-commit run --all-files`) and ensure GitHub Actions CI is green.
- Commit messages must follow repository rules (Conventional Commits + bilingual subject); do not bypass hooks unless explicitly approved.
- **`--no-verify` is strictly prohibited.** Never use `git commit --no-verify` or `git push --no-verify` to bypass pre-commit hooks. All commits must pass the full pre-commit check suite. If hooks are slow, use `git commit -m "message"` without `--no-verify` and let hooks run to completion. This rule applies to all code generation and automation tools in this workspace.
- Prefer **rebase on latest `origin/main`** before push/merge to minimize drift and conflict risk.

#### Stacked PRs (base on another branch)

When a PR depends on an unmerged PR, point its base at that branch and say so in the body — the downstream PR then needs only a re-alignment once, not a second review.

**Expect every downstream PR to turn `CONFLICTING` when its base lands.** That is bookkeeping, not a content conflict: this repo merges **rebase-only** (`allow_squash_merge` / `allow_merge_commit` are off), so landed commits get **new SHAs**; the downstream branch still carries the old ones, its merge-base drifts, and `delete_branch_on_merge` retargets the PR to `main`. The trees may be identical while the PR reports conflicts.

Re-align by rebasing (not by merging `main` into the branch):

```bash
git switch <downstream-branch>
git rebase origin/main           # git drops the commits already upstream: "skipped previously applied commit"
git diff --stat <old-head> HEAD  # empty ⇒ content unchanged, so the earlier local test results still hold
git ls-remote origin <branch>    # confirm the remote head *before* overwriting it
git push --force-with-lease=<branch>:<sha-from-ls-remote> origin <branch>
```

- Use the **explicit** `--force-with-lease=<ref>:<expected-sha>` form. The bare form compares against the local remote-tracking ref, which is stale right after a rebase (fails as `stale info`), and it cannot tell "someone else pushed" apart from "the ref is gone upstream" — the latter is exactly what happens when the base merged and `delete_branch_on_merge` removed it.
- `--force-with-lease` still needs explicit user authorization (see above): inspect, then push.
- Merging `origin/main` into the branch also clears the conflict and needs no force-push, and GitHub's rebase merge does tolerate the merge commit (it drops it). Prefer the rebase anyway: it keeps the PR's commit list and body honest about what the PR actually changes.
- A genuine content conflict is still possible when two batches touch the same lines (e.g. the migration counters in this file). Resolve by keeping the downstream side, then re-run the zero-drift tests.

### Environment variable `API_KEY`

- **Default (`llm_http_auth_mode = bearer` in config)**：`API_KEY` is the cloud vendor Bearer token (optional process fallback). **`serve` / `bench` 可在未设置 `API_KEY` 时启动**；实际调用 `chat/completions` 前须有关密钥，优先级：**请求体 `client_llm.api_key`（官方 Client）** → **环境变量 `API_KEY`**。同进程 **`repl` / `chat` / `tui` 入口与实现已硬删**（D2.2；用 Client **`crabmate-tui`**）。服务端 **不再** 读写 `client_llm` / `executor_llm` / `saved_model_*` 钥匙串槽。无 **`--config`** 且 cwd 无本地覆盖时采用 **`$XDG_CONFIG_HOME/crabmate/config.toml`**（可种子/回退 `/etc`），并合并 **`llm_overrides.json`** 与 **`prefs.json`** 的 **`cm_role`**（**不**自动打开 **`last_workspace_root`**；须 **`--workspace`**）。**`crabmate models` / `crabmate probe`** 在 `bearer` 下仍要求环境变量 **`API_KEY`** 非空。 **`config`（`cargo run -- config`）、`doctor`、`web-bearer` 与 `save-session`（别名 `export-session`）不要求 `API_KEY`**。
- **Local OpenAI-compatible backends（e.g. Ollama）**：set **`llm_http_auth_mode = "none"`**（or **`CM_LLM_HTTP_AUTH_MODE=none`**）so CrabMate does **not** send `Authorization` to `chat/completions` / `models`; then `serve` / `bench` / `models` / `probe` can run **without** `API_KEY`. With `bearer` and a wrong or missing key, chat returns an error（Web：`LLM_API_KEY_REQUIRED` 等；勿在日志中输出完整密钥）.
- **供应商配置细节（`api_base` / `model` / 认证模式 / 供应商专属开关）**：**`docs/配置说明.md`** 是唯一权威来源——**本地 Ollama**、**MiniMax**（`system` 合并、`llm_reasoning_split` 默认值、`reasoning_details` 折叠）、**智谱 GLM**（`llm_bigmodel_thinking`、最小 cURL 对齐）、**Moonshot Kimi**（`temperature` 按模型 ID 钳制、`llm_kimi_thinking_disabled`）、**火山引擎方舟**，以及思维链少复述附录（`thinking_avoid_echo_*`），均含可直接照抄的 TOML / cURL 示例。**勿在本文件复述这些细节**：改默认值或新增供应商时只改该文档，两处并列必然漂移。

### Running services

- **Backend + Web UI**: `cargo run -- serve` is **always API-only** (never hosts a SPA; the Client UI is hosted by the Client repo over CORS) and can start **without** `API_KEY` when using default `bearer`. Set the key in the Client Web sidebar (**API 密钥** → `client_llm`) or export `API_KEY`. Example: `API_KEY="..." cargo run -- serve` (default port 8080, binds **127.0.0.1** only). For LAN access use `serve --host 0.0.0.0` (see README). Optional global `--log /path/to.log` appends logs and mirrors to stderr. Without `RUST_LOG`, `serve` defaults to **info**; `bench` / `config` / `save-session` (alias `export-session`) and other non-serve subcommands default to **warn** unless you set `RUST_LOG` or `--log`. **`POST /config/reload`** (same auth as protected APIs) hot-reloads most `AgentConfig` fields without restarting `serve`; see **`docs/配置说明.md`** (**`API_KEY` 不因热重载从环境重读**；Web 密钥仍走 `client_llm`)。
- **`crabmatectl`**（独立 binary，**Linux-only**；进程身份与存活判定读 procfs，其他平台在入口以 `platform_unsupported` 拒绝）: manages local multi-instance `serve` processes (`up` / `down` / `restart` / `run` / `ls` / `status` / `logs` / `prune` / `supervise`); **no `API_KEY`**, never listens on TCP. It is a **separate binary**, not a `crabmate ctl` subcommand, and must find a sibling `crabmate` (or `CRABMATECTL_BIN`), otherwise it fails with `serve_binary_missing`. See `docs/命令行与路由.md` → 本地多实例（`crabmatectl`）.
- **CLI diagnostics**: `cargo run -- doctor` — human-readable check (Rust/tooling/workspace paths, allowlist size, redacted secrets); **no `API_KEY`**. **`crabmate web-bearer status|set|clear`** writes/reads the Web API shared secret in the system keyring (same slot as Web Settings; **`serve`** falls back when TOML/env are empty); prefer **`set --stdin`** / **`set --from-env`** / interactive prompt so the secret is not on argv; **no `API_KEY`**. **`save-session`** exports chat JSON/Markdown to `<workspace>/.crabmate/exports/` (same shape as Web; alias `export-session`); **no `API_KEY`**. **`mcp list`** / **`mcp list --probe`** require the **`mcp`** Cargo feature (`cargo build --features mcp`); prints the in-process MCP stdio session cache when MCP is enabled in config; **no `API_KEY`**. `cargo run -- models` / `probe` use `GET {api_base}/models` with Bearer only when `llm_http_auth_mode=bearer`; with `none`, no `Authorization` header is sent.
- **`serve` never hosts a UI.** Build the Client UI from the sibling repo (`cd ../crabmate-client && make frontend`; clone [crabmate-client](https://github.com/noisystreet/crabmate-client) as a sibling first) and host it there; it connects to `serve` over CORS (**`CM_WEB_CORS_ALLOWED_ORIGINS`** for extra browser Origins).
- **E2E tests** (Playwright): owned by Client [`e2e/`](https://github.com/noisystreet/crabmate-client/tree/main/e2e)（`./scripts/e2e-playwright.sh` 转发到同级仓，可用 **`CRABMATE_CLIENT_DIR`**）。Proxy tip: `no_proxy=127.0.0.1,localhost`.
- Debug / troubleshooting: see **`docs/调试指南.md`** (Chinese, with English companion **`docs/en/DEBUG.md`**), including **`CM_WEB_DISABLE_MARKDOWN`** (plain-text bubbles), **`CM_WEB_RAW_ASSISTANT_OUTPUT`** (skip assistant display filters), and **`GET /web-ui`** (restart `serve`; no TOML keys), logging, `doctor`, SSE alignment, and related **`docs/配置说明.md`** links.

### Gotchas

- **排障摘要**：模型可调用工具 **`diagnostic_summary`**（参数均可选）收集只读、脱敏信息：Rust 工具链版本、`target/` 与常见路径是否存在、关键环境变量是否已设置（**不输出任何变量值**；与 `API_KEY` 同类变量亦不报告长度）。勿将真实密钥粘贴进对话或工具入参。
- The project uses Rust **edition 2024**, which requires **Rust 1.85+**. The VM snapshot installs the latest stable toolchain. If `cargo build` fails with an edition error, run `rustup update stable && rustup default stable`.
- **Rust nightly** is pre-installed in the environment. You can use `cargo +nightly test` and similar commands directly.
- System libraries `libssl-dev` and `libssh2-1-dev` are required for the Rust build (installed by the VM snapshot).
- **长期记忆（fastembed，可选 Cargo feature）**：默认构建**不**链接 **`fastembed`**；需语义向量检索或 **`codebase_semantic_search`** 时请 `cargo build --features fastembed`（或 `--all-features`）。启用后依赖 ONNX Runtime 与 **libstdc++**；模型缓存目录为 **`$XDG_CACHE_HOME/crabmate/fastembed`**（可用 **`CM_CRABMATE_CACHE_DIR`** 覆盖根路径）；仓库根 **`.cargo/config.toml`** 在 Linux x86_64 上将链接器设为 **`gcc`**，以便正确解析 `-lstdc++`。若链接失败，请安装 **`g++`**（或等价的 `libstdc++` 开发包）后再构建/测试。
- Web 会话默认落盘到工作区 **`.crabmate/conversations.db`**（**`conversation_store_sqlite_path`**；可在配置中清空以关闭）；**`rusqlite` bundled** 特性（经 **`libsqlite3-sys`** 自带 SQLite）；无需系统 **`libsqlite3`**。
- `clang-format` is used by `format_files` for C/C++ sources. If missing, `/health` may report `dep_clang_format` as degraded; C/C++ formatting tools will return an explanatory error. For check-only runs use `run_command` (`clang-format --dry-run --Werror <file>`).
- `cmake` and `ctest` are on the `run_command` allowlist for configuring/building/testing CMake projects. If missing, `/health` may report `dep_cmake` / `dep_ctest` as degraded. `mkdir` is also allowlisted for script-style directory creation (same argument rules as other `run_command` invocations). Note: `run_command` rejects any arg containing `..` or starting with `/`, so prefer relative `-S`/`-B` and `--build` paths (avoid absolute `-D` values in args).
- `c++filt` (Itanium demangler) is on the default `run_command` allowlist for demangling linker/stack symbols. If missing, `/health` may report `dep_cxxfilt` as degraded.
- GNU **Binutils**-style tools on the default `run_command` allowlist for read-only binary inspection: `objdump`, `nm`, `readelf`, `strings`, `size`, and `ar`. If missing, `/health` may report `dep_objdump` / `dep_nm` / `dep_readelf` / `dep_strings_binutils` / `dep_size` / `dep_ar` as degraded. Same `run_command` rules: no `..` or `/`-prefixed args.
- **`npm`** and **`python3`** are on the default `run_command` allowlist (e.g. for lint/build/test suggestions the model derives itself). If missing, `/health` may report `dep_npm` / `dep_python3` as degraded; related commands will fail until installed.
- `autoreconf`, `autoconf`, `automake`, and `aclocal` are on the default `run_command` allowlist for Autotools maintenance; they execute project `configure.ac` / `Makefile.am` logic—only use in trusted workspaces. For a narrower allowlist (e.g. in production), override **`allowed_commands`** in your config or set **`CM_ALLOWED_COMMANDS`**; defaults ship in **`config/tools.toml`**.
- Default **`allowed_commands`** includes common Linux utilities (e.g. `stat`, `grep`, `diff`, `jq`, `ps`, `zcat`), **`python3` / `npm`**, **`bash` / `sh`** (for **`bash -c` / `sh -c`** when you need `&&` / pipes / `;` in one shot—equivalent to arbitrary command execution), and **`git` / `gh` / `cargo` / `rustc`**; they can modify repos or run build scripts—treat workspaces as trusted.
- **GitHub CLI `gh`** is on the default `run_command` allowlist. If not installed, **`GET /health`** reports **`dep_gh`** as degraded (like other optional CLIs); install `gh` and run **`gh auth login`** (or equivalent) for API access.
- Static-analysis / lint CLIs (`shellcheck`, `cppcheck`, `semgrep`, `hadolint`, `bandit`, `lizard`) are on the default `run_command` allowlist and are invoked via generic `run_command` (the dedicated `shellcheck_check` / `cppcheck_analyze` / `semgrep_scan` / `hadolint_check` / `bandit_scan` / `lizard_complexity` tools have been removed). `/health` no longer probes them, so there are no `dep_shellcheck` / `dep_cppcheck` / `dep_semgrep` / `dep_hadolint` / `dep_bandit` / `dep_lizard` entries; missing-CLI install hints now come from the model reading `run_command`'s failure output. These are read-only analysis commands and do not modify files.
- **Lint**：仓库 **pre-commit** 使用 **`cargo clippy --all-targets --all-features -- -D warnings`**（见 **`.pre-commit-config.yaml`** 与上文 **Repository engineering rules → Commit & push**）。**提交前**须通过；仅本地快速试探时可运行不带 `-D warnings` 的 **`cargo clippy`**，但不应在 hook 未通过时代为提交。
- **`cargo fmt --check`**：若与 **`cargo fmt`** 结果不一致，先执行 **`cargo fmt --all`** 再提交；pre-commit 也会格式化 Rust 代码。
- The `rfd` crate (file dialog) is a dependency but won't work headlessly; this doesn't affect the web server mode.
- **pre-commit install** may fail with `core.hooksPath` set. Run `git config --unset-all core.hooksPath` first, then `pre-commit install && pre-commit install --hook-type commit-msg`.
- When starting the server with `--host 0.0.0.0` (non-loopback), you must either set `CM_WEB_API_BEARER_TOKEN` or `CM_ALLOW_INSECURE_NO_AUTH_FOR_NON_LOOPBACK=true`; otherwise the server refuses to start.
- **Temporary skip of Web Bearer while testing**: middleware checks only when the server secret is non-empty. Prefer `unset CM_WEB_API_BEARER_TOKEN` (and clear TOML **`web_api_bearer_token`**) then **`serve --host 127.0.0.1`**. For **`0.0.0.0`** without auth: clear the secret first, then **`CM_ALLOW_INSECURE_NO_AUTH_FOR_NON_LOOPBACK=true`** (trusted LAN only; a non-empty secret still yields 401). See **`docs/配置说明.md`**.
- Optional hardening: set **`web_api_require_bearer=true`** and a non-empty **`CM_WEB_API_BEARER_TOKEN`** / **`web_api_bearer_token`** / **`crabmate web-bearer set`** before **`serve`** so startup fails without a shared secret; embedded default is **`web_api_require_bearer=false`** (UI can load without server-side token, but protected routes stay open until you configure a secret—see auth middleware). The browser must also save the **same** shared secret under Web **Settings → “Web API shared secret (Bearer)”** (in-page + **`localStorage`** key **`crabmate-api-bearer-token`**); this is **not** the LLM **`API_KEY`**. See **`README.md`** / **`docs/配置说明.md`**.

## Repository engineering rules

**This section is authoritative for agents and is the only rule source.** The former `.cursor/rules/*.mdc` files (and the `.trae/rules/` copy) are deleted — do not reintroduce them; edit this section instead.

### Local quality entry points

Three entry points exist and they are **not** interchangeable — running the wrong one is how “local was green, CI went red” happens:

| When | Command | Covers |
|------|---------|--------|
| Before every commit | `pre-commit run --all-files` | `cargo fmt`, `cargo clippy -D warnings`, `cargo doc` (rustdoc warnings denied), crate-dep policy, lizard CCN, fn param/nloc ratchets, builtin tool-name literal ratchet, `taplo` |
| Build / package | `make backend` / `make package` (see `make help`) | Compilation and release artifacts; **not** a gate |
| Full test suite | `make test` (i.e. `cargo test --workspace`) | Also run in CI |

- **`pre-commit` deliberately does not run `cargo test`** (goldens included); `cargo test` runs in CI (`ci.yml`, `code-complexity.yml`). So “pre-commit passed” never means “tests passed”.
- `ci.yml` runs `cargo check --workspace --all-targets --all-features`, `cargo check -p crabmate`, the crate-dep policy script, `cargo clippy … -D warnings` and `cargo test --workspace`. Pick the matching local command from the test-scope table in **Commit & push** rather than guessing.
- Do not add a slower check to the pre-commit hooks just to mirror CI; keep the commit hook fast and let CI own the expensive jobs.

### Commit & push

- Before **every** `git commit`: `pre-commit run --all-files`. If `pre-commit` is not installed, run at least, from the repo root: `cargo fmt --all`; `cargo clippy --all-targets --all-features -- -D warnings`; `bash scripts/lizard-rust.sh` (Rust CCN ≤ 10); `bash scripts/fn-param-ratchet.sh` (≤ 9 params); `bash scripts/fn-nloc-ratchet.sh` (fn nloc ≤ 200, file ≤ 920 lines); `bash scripts/tool-name-literal-ratchet.sh` (no new builtin tool-name literals at comparison / match / or-pattern sites — use `crate::cm_names::*`, see `#1155`).
- Fix hook failures and re-run until green; `git add` any file the hooks rewrote, then commit. **`--no-verify` is prohibited** — if the user explicitly demands an exception, state the risk in the reply.
- **Subject format**: `type(scope): 中文简述 / English brief` — Conventional Commits + bilingual, `scope` written **once in English**, both sides verb-first and symmetric. Mark incompatible changes with `!` after the type/scope or a `BREAKING CHANGE:` footer. Bare messages like「更新」「修改」are rejected by the `commit-msg` hook.
- **Before `git push`**: `git fetch origin main` → `git rebase origin/main` → resolve conflicts (`git add` + `git rebase --continue`) → re-run the checks above → push. A `--force-with-lease` needed by the rebase requires explicit user authorization.
- **`cargo test` is not part of pre-commit.** Scope it yourself:

| Change | Test scope |
|--------|-----------|
| Single module / file | `cargo test -p crabmate <filter>` or just the related tests |
| `Cargo.toml`, workspace, cross-module types, `src/lib.rs` / public API, protocol / SSE / config loading | full `cargo test` |
| Pre-merge, release, CI alignment | full `cargo test` |

- New logic without test coverage: add a unit or minimal integration test if feasible; if not, state the risk and plan in the PR / reply.

### Rust error handling

- **No bare `unwrap()` / `expect("…")` on production paths.** Prefer `?` plus context (`.map_err` with an explanation).
- `expect` is allowed only where the invariant is documented in the message: startup-path init in `src/main.rs` that should abort the process anyway, and one-shot `LazyLock` / `OnceLock` initialization. `#[cfg(test)]` / `tests/` / `benches/` may use them freely, but failure messages must stay readable.
- **`unsafe`: do not write it by default.** If unavoidable — smallest possible scope, a comment directly above the block stating *why it is sound* (invariant, preconditions, which FFI/library contract it binds), and never copy the same unsafe logic in several places without wrapping it.
- `panic!` is for unreachable branches only, never for expected IO/parse failures (return `Result`).

### Secrets & logging

- Never put real **API keys, tokens, private keys, DB passwords** into `src/`, `config/*.toml`, fixtures, scripts, **commit messages**, PR/Issue bodies, or comments that look like real values.
- `.env` / `.env.*`: keep local only (gitignored); never paste their **contents** into chat, docs, patches, or screenshots. Examples use placeholders (`YOUR_DEEPSEEK_API_KEY`); any `sk-…` sample must be marked fictitious.
- If a real secret was committed: **rotate it immediately** and rewrite history — a plain `git revert` is not enough.
- `tracing` / `log` / `eprintln!` / error strings returned to clients: never emit a full key, a whole `Authorization: Bearer …`, or a URL carrying a real `?key=` / `?token=`. Log only *whether set*, length, or a few leading/trailing chars (or use the shared redact helpers).
- Tool arguments, subprocess stdout, and third-party response bodies may contain credentials — truncate/redact before writing them to disk or logs. User-facing text stays generic (e.g.「API 密钥无效」).
- While reviewing a diff, check for newly added key-shaped constants and for `std::env` / `process.env` values concatenated straight into logs.

### Security-sensitive surfaces

When touching any of these, explicitly check the boundary and state risk + mitigation in the PR / reply:

| Area | Entry points | Focus |
|------|--------------|-------|

### Architecture & documentation sync

- Changing **architecture** or `src/` module organization ⇒ review and update `docs/开发文档.md`: the「架构设计」section (layering, Web data-flow summary, Mermaid nodes/edges) and the「主要模块」responsibility table. Keep it an overview — details belong in topical docs; do not re-grow a per-file table there (tool inventory lives in `docs/工具说明.md` / the registry).
- Triggers: adding/removing `mod` in `src/lib.rs`, reorganizing `Router` / `AppState`, creating/renaming/deleting `src/` files or directories, a file's primary responsibility changing, `tool_registry` gaining a new execution class, `runtime/` / `web/` submodule boundaries moving.
- Not needed: pure implementation changes, private renames, comments/formatting, `tests/` / `#[cfg(test)]` / fixtures only.
- **User-visible changes** (CLI flags, API, config keys, TUI/Web behavior, tools) ⇒ also `README.md` (usage) and `docs/工具说明.md` (tools). Internal refactors with no behavior change may update only `DEVELOPMENT.md` / comments.
- Changing `config/*.toml`, axum routes/handlers (path, method, request/response body, new endpoints), or adding/renaming/removing a `CM_*` env var ⇒ **must** update `README.md` (users: how to configure, defaults, names) and `docs/开发文档.md` (maintainers: key meaning, module boundaries).
- `docs/待办清单.md`: delete an item once implemented (never park `- [x]` entries; use git history for "when"); drop a heading when its last item is gone.

### Release & versioning

**Single source of version truth: `Cargo.toml` → `[package] version`.** There is no separate version file to keep in sync.

- **Tag format**: `vX.Y.Z`, optionally `vX.Y.Z-rc.N`. `.github/workflows/release.yml` rejects anything not matching `^v[0-9]+\.[0-9]+\.[0-9]+([.-].*)?$`, and **fails the run** when the tag's core `X.Y.Z` does not match `Cargo.toml`. A prerelease tag (`v0.1.0-rc.1`) is allowed while `Cargo.toml` stays at `0.1.0`.
- **Cut the CHANGELOG before tagging**: the workflow extracts the `## [X.Y.Z]` section from `CHANGELOG.md` as the GitHub Release body; a missing section yields a stub body plus a warning. So “move `[Unreleased]` into `## [X.Y.Z]`” is part of the release, not an afterthought.
- **Pushing the tag is the release**: it builds the `tar.gz` / `.deb` artifacts and creates or updates the GitHub Release (re-running the same tag updates the existing one; `workflow_dispatch` accepts an existing tag for a manual rebuild). Local equivalent for verification: `make package` → `dist/`.
- `client-contract-v*` tags belong to the **Client repo** (`crabmate-client`) contract pin and are outside this repo's release flow — do not reuse this repo's `v*.*.*` tags for it.
- A change that breaks config keys, SSE/HTTP contracts or the public CLI is a **breaking change**: mark it in the commit subject (`!` or `BREAKING CHANGE:` footer) **and** call it out in the CHANGELOG entry. See **Architecture & documentation sync** for the docs that must move with it.

### CHANGELOG

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and is **English-primary** (matching `README.md`). Entries accumulate under `## [Unreleased]`, grouped as `Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security`; the release step moves them into a version section (see **Release & versioning**).

- **Must be recorded**: user-visible behavior (CLI flags, routes, config keys, `CM_*` env vars, tool add/remove/rename, SSE/HTTP contract changes), behavior fixes, dependency changes with user impact, and every breaking change.
- **Need not be recorded**: internal refactors with no behavior change, comments, tests, formatting, typo fixes in docs, and `agent_space/` drafts.
- Write the **why and the user-visible consequence**, not a restatement of the diff. Long entries are acceptable here (existing entries run to a full paragraph); keep secrets, keys and internal hostnames out.
- Going forward from a deleted/deprecated capability, say so explicitly (`Removed`) rather than silently dropping the line — the D2.2 `repl` / `chat` / `tui` removal is the reference case.

### Dependencies & licenses

Triggers: edits to the root `Cargo.toml` / `Cargo.lock` (new crate, major bump, new feature); shell dependencies live in the Client repo (`../crabmate-client/desktop-tauri/src-tauri/Cargo.toml`).

- Check the new crate's **license** against how the project is distributed; watch **copyleft** (GPL) and **network clauses** (AGPL). `deny.toml` backs `cargo deny check licenses bans sources` (CI: `.github/workflows/dependency-security.yml`) — a new identifier not in the allowlist means updating `deny.toml` **with a stated reason**.
- `cargo audit` covers known vulnerabilities; it and `cargo deny` advisories are intentionally split (see `docs/开发文档.md`).
- Keep lockfiles (`Cargo.lock`, `package-lock.json`) consistent with the manifests so reproducible builds hold.
- Local path / git dependencies: explain the source and update strategy in the PR or `docs/开发文档.md`.
- This is not legal advice; material compliance decisions need a human.

### CLI / TUI / Web shared logic

After D2.2 the in-process `chat` / `repl` / `tui` are hard-deleted. Surfaces: this repo's ops CLIs (`serve`, `doctor`, `web-bearer`, `save-session`, `tool-replay`), Client **`crabmate-tui`** (HTTP + SSE), Client Web/Desktop UI (this repo's `lib` HTTP + SSE).

- For each new capability, first decide whether it is **inherently one surface** (Web-only route, TUI-only shortcut, ops-only subcommand form).
- If **not** inherent: make it reachable from the ops CLI, `crabmate-tui`, and Web; differences should be interaction and presentation only.
- If **inherent**: implementing it on one surface is fine, but the **data model, tool execution and config keys** still belong in the shared layer (`agent/`, contract types) so the others can adopt it.
- Put UI-independent rules in reusable modules (`agent/`, `types`, `sse::protocol`, `tool_registry`, UI-agnostic parts of `runtime/`); session/export shapes already live in `runtime/workspace_session` and `runtime/chat_export` — extend the same contract.
- Pure UI details (keyboard, focus, components, terminal drawing) and genuinely surface-specific needs are exempt, but core data structures and tool execution still go through the shared layer.
