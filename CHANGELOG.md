## [Unreleased]

### Added

- **`modify_file` gained `expect_first_line` / `expect_last_line` for line-range guards**: `expect_content` validates a replaced range line by line, which is exact but forces the caller to re-transcribe the whole span — painful for deletions, where the block often starts or ends on a blank line and every `\n` has to be hand-written (a slip is only caught by `dry_run`). The new pair anchors just the first (`start_line`) and last (`end_line`) line of the range, enough to prove "this is the block I meant". They are **mutually exclusive** with `expect_content` (supplying both is rejected rather than silently picking one), are rejected for `insert_after_line` (that keeps `expect_line_content`), and work in both top-level `replace_lines` and per-edit `edits[]` replace entries. Failure text matches `expect_line_content`: actual content plus the relocate hint (`实际位于行 N` / `出现 N 处` / `未找到`), so a drifted line number self-corrects. Pinned by five tests in `tests_guards_batch.rs`. See `docs/工具说明.md`.

- **`GET /status` reports the tool-definition token cost**: new optional field **`tiktoken_tool_definitions_tokens`** on the full (non-`view=shell`) status payload — the `tiktoken` estimate for the serialized **`tools`** array. It closes the last blind spot of the per-request fixed prefix: `tiktoken_new_session_baseline_by_agent_role` counts `messages` only, so tool JSON (the single largest fixed constant once the registry reaches three digits) was invisible. Computed once per **300s** — same TTL as the baseline cache, keyed by model + tool count + first/last tool name — via `spawn_blocking`, then cached. The value is an **upper bound** for "Act + a role without `allowed_tools`": Ask/Plan and role-filtered turns narrow the array at turn-execution time (`run_dispatch` / `session_mode_turn`), which this view cannot see. Reports `0` under `--no-tools`; the key is omitted when serialization fails. See `docs/命令行与路由.md`.

### Changed

- **The five read-only `file_core` tools moved to typed runners, and their argument/path errors carry explicit codes**: `read_dir` / `glob_files` / `list_tree` / `read_binary_meta` / `hash_file` signalled failure by writing a `String` whose first line `parse_legacy_output` had to classify. Every branch did get a verdict — but from unrelated substrings: metadata / open / read failures pass only because their text happens to contain `失败` (`打开文件失败: …`, `读取元数据失败: …`), and argument errors survive on the `错误：` prefix — collapsing all of them onto the generic `{tool}_failed` / `external` regardless of the actual cause. Two branches were worse than they looked in a subtler way: `read_binary_meta` / `hash_file`'s workspace-path failures did route through `tool_user_error_from_workspace_path(e)`, whose `prefixed_user_message()` starts with `错误：`, so `looks_like_failure` already marked them failed — but every cause (escaping the workspace root, a missing file, an absolute path, an empty path) collapsed onto the generic `{tool}_failed` / `external`. (An earlier draft of this entry claimed those branches came back as `ok: true`; that was wrong — the `错误` prefix is enough for `looks_like_failure`. The real defect was the loss of cause, not a false success.) They now return `Result<String, ToolError>` (per-module `*_try` behind the shared `define_runners_cwd_try!` macro), taking the Legacy ratchet baseline **49 → 44** (46 → 41 with `archive-tools`). Tool names, descriptions and parameter schemas are unchanged, and **success bodies are byte-identical** — the `crabmate_tool_output` v1 headers of `read_dir` / `list_tree` and `hash_file`'s `digest_hex:` line are pinned by existing tests routed through an `out_str(...).expect("expected success")` helper. The failure surface only gains sharper codes, all registered in `failure_category_for_error_code`: argument / JSON errors become `invalid_args`, "not a directory / not a file" preconditions become **`read_dir_path_not_dir`** / **`glob_files_path_not_dir`** / **`list_tree_path_not_dir`** / **`read_binary_meta_path_not_file`** / **`hash_file_path_not_file`** (`invalid_input`), the `*_workspace_resolve_failed` / `*_workspace_root_resolve_failed` family reports `workspace` (**now only** when the path escapes the workspace root or the root itself cannot be resolved — a missing target is an IO failure; see `workspace_path_tool_error` in `src/cm_tools/tools/file/path.rs`), sensitive-path rejection on `read_dir` (`/proc` / `/sys` / `/dev` / `/root` / `/etc`) becomes **`read_dir_sensitive_path`** (`policy_denied`), and metadata / open / read plus path-resolution failures become **`read_dir_io_failed`** / **`glob_files_io_failed`** / **`list_tree_io_failed`** / **`read_binary_meta_io_failed`** / **`hash_file_io_failed`** (`external`; the last two already existed, the first three are new, and all five are listed explicitly in `failure_category_for_error_code` instead of relying on the `ends_with("_failed")` fallback). Message texts are unchanged, including the two branches described above; the regression pins create a real file in the workspace's parent directory so that `OutsideWorkspaceRoot` (not `PathResolveFailed`) is actually exercised, and two further cases pin missing targets onto the `*_io_failed` codes. `repo_overview_sweep`'s internal aggregation of `list_tree` / `glob_files` keeps its byte-identical contribution by routing through `*_try(..).unwrap_or_else(|e| e.message)` (the error body is the same text the legacy facade returned), so the `String` facades (`file::read_dir` / `glob_files` / `list_tree` / `read_binary_meta` / `hash_file`) are deleted with no orphaned consumers, and the stray `pub use file::list_tree` re-export in `tools/mod.rs` goes with them. Docs: the per-tool `error_code` lists in `docs/工具说明.md` gained the new stable codes, and the stale "SHA-256 / SHA-512 / BLAKE3" claim on `hash_file` was corrected to SHA-256 / SHA-512 only (what the implementation actually accepts; `read_binary_meta`'s prefix hash is also SHA-256 only).

- **`text_transform` moved to a typed runner, closing three silent-success branches**: it signalled failure with `String` bodies whose first line matched none of the keywords `parse_legacy_output` scans for, so `text 过长：N 字节，上限 M`, `delimiter 过长：…` / `lines_split 必须提供非空 delimiter`, and `切分后段数 N 超过上限 M` all came back **`ok: true`**. It now returns `Result<String, ToolError>` (`run_try`, behind a hand-written `runner_text_transform_try` — the args-only macro has no Typed twin), taking the Legacy ratchet baseline **51 → 49** (48 → 46 with `archive-tools`) together with `structured_patch` below. Success bodies are unchanged; those three branches plus `Base64 解码失败：…` and `URL 解码失败：…` now report `invalid_args`. Two things worth recording: a non-UTF-8 Base64 result keeps returning **success** with a hex preview (unchanged — that output *is* the answer), and the plan's worry about `urlencoding::decode` returning `Ok` on invalid UTF-8 did **not** hold: it already mapped `Err` to `URL 解码失败`. Pinned by `oversized_text_is_invalid_args` / `lines_split_without_delimiter_is_invalid_args`.

- **`structured_patch` moved to a typed runner, the last mutating tool on the legacy surface**: two branches were silently `ok: true` — `read_limited`'s errors were forwarded as a bare `e.to_string()` (no `错误：` prefix, no keyword), and `parse_patch_query_tokens` reports `query 无效: …` — so a patch against an oversized or unreadable file, or with a malformed path expression, came back successful. The whole chain (`run_structured_patch` / `prepare_structured_patch` / `detect_structured_patch_format` / `read_limited_json_value` / `apply_patch_mutation` / `finish_structured_patch`) now returns `Result<String, ToolError>`. Codes: `invalid_args` for argument / query / revision-guard / csv-tsv / patch-application problems, **`structured_io_failed`** (shared with the read-only `structured_*` tools through the same `structured_io_error` helper) + **`structured_patch_parse_failed`** on the read side, **`structured_patch_serialize_failed`** for serialization, and **`structured_patch_write_failed`** for the atomic-commit path. That last one was *not* silently succeeding — its text contains `失败`, so it was already judged failed — but it collapsed onto the generic `structured_patch_failed` / `external`, which is exactly the code a caller should be able to act on, so it now reports the specific one. **`dry_run` still defaults to `true`**, and the preview / write bodies are byte-identical; `read_limited`'s errors keep their text but gain the `错误：` prefix (that prefix is what made them fail at all). Pinned by six existing `tests_revision` cases (now routed through a local `run_str`), the new `structured_patch_over_long_query_segment_is_invalid_args`, and the legacy-ratchet baseline; `file/tests_guards_batch.rs` calls `structured_patch_try(..).expect(..)`. **`structured_patch_write_failed` itself has no test**: provoking it needs a read-only parent directory, and `chmod` is not enforced when the suite runs as root (the usual CI-container case), so such a test would be flaky rather than reassuring.

- **`markdown_check_links` and the three read-only `structured_*` tools moved to typed runners, closing one more silent-success branch plus one defence-in-depth gap**: the helpers behind the three `structured_*` tools (`read_limited` / `detect_format` / `parse_to_json`) report failures as `String`, and most of those began with `错误：`, so `parse_legacy_output` did judge them failed — but `structured_diff`'s `detect_format(path_a, fmt_override)?` propagated a bare `无法从扩展名推断格式，请显式传 format…` (no prefix, no keyword) and came back `ok: true`. `markdown_check_links`'s `参数 JSON 与 markdown_check_links 形状不一致: …` has the same shape, but is **unreachable from the tool surface** — `tool_args_validate` rejects those payloads first against the same `MarkdownCheckLinksArgs`, so it can only be hit by the internal caller — making that one a defence-in-depth fix in the `env_var_check` tradition, not a daily-path one. They now return `Result<String, ToolError>` (`structured_validate_try` / `structured_query_try` / `structured_diff_try` / `markdown_check_links_try`, the last delegating to `markdown_check_links_inner_try`), taking the Legacy ratchet baseline **55 → 51** (52 → 48 with `archive-tools`). Tool names, descriptions and schemas are unchanged, and **success bodies are byte-identical** — `validate_ok_body_is_verbatim` pins the `校验通过: …\n格式: Json\n` head. The rest of the surface only gains sharper codes: argument / extension-detection problems become `invalid_args`, `read_limited` splits between `invalid_args` (`文件过大`) and **`structured_io_failed`** while keeping the `错误：…` body prefix, parse failures become **`structured_parse_failed`**, and path resolution reports `workspace_resolve_failed` / **`markdown_check_links_workspace_failed`** / **`structured_diff_path_{a,b}_resolve_failed`** (the last two keep their original `错误 path_a: …` text, which already failed before). `structured_patch` deliberately stays `Legacy` — it writes to disk and belongs with the mutating batch. Two consumers had to move with it: `docs_health_sweep` now matches on the `Result`, but keeps its own `markdown_links_failed` predicate (`结论: 发现` means *link problems were found*, not *the tool failed*), and the six `markdown_links` module tests call `markdown_check_links_try(..).expect(..)`. Pinned by `structured_data`'s `validate_missing_path_is_invalid_args` / `validate_ok_body_is_verbatim` / `diff_unknown_extension_is_invalid_args` / `query_missing_query_is_invalid_args` / `query_ok_body_is_verbatim`, `markdown_links`'s `missing_workspace_root_reports_workspace_failed`, and the legacy-ratchet baseline.

- **`text_diff` / `table_text` moved to typed runners, and their parameter errors stop being reported as success**: both signalled failure by writing a `String` whose first line `parse_legacy_output` had to classify — but its keyword table is only `错误` / `未知工具` / `参数解析错误` / `执行失败` / `失败` / `超时`, so **every argument-check branch was silently `ok: true`**: `文件过大：N 字节，上限 M`, `left 过长` / `right 过长`, `text 过长`, `mode 仅支持 inline 或 paths`, `context_lines 须在 0～20 之间`, `inline 模式需要 left（字符串）`, `paths 模式需要 left_path`, `delimiter 仅支持 auto、comma/csv…`, `filter_rows 需要 column`, `aggregate 需要 column/op`, `columns 不能为空`. They now return `Result<String, ToolError>` (per-module `run_try` behind the shared `define_runners_cwd_try!` macro), taking the Legacy ratchet baseline **54 → 52** (57 → 55 with `archive-tools`). Tool names, descriptions and schemas are unchanged, and **success bodies are byte-identical** — `preview_inline_keeps_body_verbatim` pins `table_text`'s `delimiter=…` head. On the failure side the previously-broken verdicts become `invalid_args` / `invalid_input`, while the branches that already failed keep their text but sharpen their codes: path resolution now reports **`workspace_resolve_failed`** / `workspace` (previously the generic `{tool}_failed` / `external`) via `ToolError::path_resolve_failed` — the body still reads `错误：…` because that helper's `prefixed_user_message` is exactly `错误：{user_message}` — and metadata / read / open failures become **`text_diff_io_failed`** / **`table_text_io_failed`**, with CSV parse errors on **`table_text_parse_failed`**. One branch is deliberately *not* `invalid_args`: `aggregate.op`'s value set is enforced by the `TableTextAggregateOp` enum during deserialization, so a bad `op` fails as `invalid_args` at the serde layer and never reaches `run_aggregate` (covered by `aggregate_without_op_is_invalid_args` on the missing-`op` path instead). The `run` String facades were deleted — no internal consumer was left (the only other reference was a rustdoc link, retargeted at `run_try`) — and module tests call `run_try` directly. Two supporting changes came with it: `failure_category_for_error_code` now maps the three new codes explicitly instead of relying on the `ends_with("_failed")` fallback, and gained a `*_serialize_failed` / `*_internal` arm ordered **before** that fallback so re-deriving a category from the code agrees with `ToolError::internal_code`'s `Internal` (`json_format_serialize_failed`, added earlier, was misclassified as `external` until now). Pinned by `text_diff`'s `unknown_mode_is_rejected_before_runner` / `missing_inline_operand_is_invalid_args`, `table_text`'s `missing_source_is_invalid_args` / `aggregate_without_op_is_invalid_args` / `preview_inline_keeps_body_verbatim`, `typed_parameter_error_without_keyword_reaches_string_surface_with_code` (the `String` surface the main agent actually reads), `typed_ok_body_is_not_stamped_with_a_header`, and the legacy-ratchet baseline.

- **Four `Basic` tools moved to typed runners, so their failures carry explicit error codes**: `regex_test` / `date_calc` / `json_format` / `env_var_check` used to signal failure by writing「错误：…」as the first line of a `String`, which `parse_legacy_output` then had to infer back into an `ok` flag and an `error_code` — so all four collapsed onto the generic `{tool}_failed` with `failure_category = external`. They now return `Result<String, ToolError>` (a `run_try` per module behind a one-line `Typed` runner), taking the Legacy ratchet baseline from **58 → 54** (61 → 57 with `archive-tools`). Tool names, descriptions and parameter schemas are **unchanged**, and **success** bodies are byte-identical — pinned by `misc_basic_typed_ok_keeps_body_verbatim`, which compares `json_format`'s output against the exact pretty-printed text. The failure surface does change, and it is worth reading twice: (1) argument and parse errors now report **`invalid_args`** with `failure_category = invalid_input` instead of `{tool}_failed` / `external`, and an uncompilable pattern gets its own **`regex_test_invalid_regex`** (same `invalid_input` family as `search_in_files_invalid_regex`), registered in `failure_category_for_error_code`; (2) `env_var_check`'s `参数 JSON 无效: …` branch was **silently reported as success** — the text matches none of the keywords `parse_legacy_output` scans for (`错误` / `失败` / `超时`), so a malformed `names` value came back `ok: true`; it now fails as `invalid_args`. That branch is effectively unreachable from the tool surface (`tool_args_validate` rejects the same payloads first, against the same `EnvVarCheckArgs`), so it is a defence-in-depth fix rather than a daily-path one. Two consequences worth naming: a **serialization** failure in `json_format` (where the `serde_json::Value` has already parsed) is now `json_format_serialize_failed` / internal rather than a success body reading「序列化失败」; and because these four echo user text back, a **successful** call whose output happens to contain「失败」/「超时」(formatting JSON that contains that word, say) now gains a one-line `crabmate_tool_output` header — the same trade-off `read_file` already makes, accepted here rather than special-cased. Their four `Legacy` runners and the `run` String facades were **deleted**, since no internal consumer was left (`file` tools keep theirs because `create_file` is still called directly); module tests go through a local `run_str` helper. Pinned by `misc_basic_typed_error_codes`, `misc_basic_typed_failure_reaches_string_surface_with_code` and the legacy-ratchet baseline. No user-facing tool surface changed, so `docs/工具说明.md` / `docs/en/TOOLS.md` are untouched.

- **BREAKING: the four read-only code-navigation tools are now one `code_nav` tool with an `action` selector**: `find_symbol` / `find_references` / `rust_file_outline` / `call_graph_sketch` were four specs across three modules (`symbol` / `code_nav` / `call_graph_sketch`) whose parameters repeated `path` / `symbol` / `max_results` / `include_hidden` two to four times each in the always-resend `tools` array. They are now one spec (`CodeNavArgs` + `CodeNavAction` = `find_symbol` / `find_references` / `file_outline` / `call_graph_sketch`), taking the Legacy ratchet baseline from **61 → 58** (64 → 61 with `archive-tools`) and shrinking the `text_code_nav` shard from four descriptions to one. **Unlike `gh_pr` / `reminder`, this merge costs no read-only semantics**: every action is read-only, so `code_nav` stays out of `builtin_write_effect_tools()` and keeps the parallel read-only batch, read-only retry, `Ask`/`Plan` gating and the read-only TTL cache — `tool_name_implies_readonly_probe` now keys on `code_nav` alone. The four implementations are **unchanged**: `code_nav_dispatch` only adapts `action` → the per-action DTO (one extra JSON round-trip on small payloads), so the verified search / outline / scoring flows are not rewritten. Required-field rules the union cannot express (`find_symbol` / `find_references` want `symbol`, `file_outline` wants `path`, `call_graph_sketch` wants `symbol` or `symbols`) now live in the dispatcher with actionable messages, and a call with no `action` at all returns the list of accepted values instead of a bare serde "missing field". Two deliberate schema choices, both spelled out in the tool description: fields irrelevant to the chosen `action` are **ignored** rather than rejected (unknown keys still fail through `deny_unknown_fields`), while the schema ranges themselves keep applying to **every** call regardless of action — `max_results: 0` is rejected even for `file_outline`, which never reads it; and `max_results` is declared `1..=300` — the wider of the two former caps — because one `schemars(range)` covers every action; `find_symbol` still clamps to 200 inside its own implementation, so the only behavior change is that a `max_results` between 201 and 300 is now **accepted and clamped** rather than rejected by schema validation. **Breaking**: `allowed_tools` entries, workflow `tool_name`s, agent-role lists and saved sessions naming any of the four must switch to `code_nav` + `action`; the built-in `refactor_precheck` template, `fixtures/workflows/04_loop_for_each.yaml` (+ `.expected.json`), `docs/工作流编写教程.md` and `docs/工作流Markdown作者层设计.md` were updated here. Pinned by `code_nav_schema_requires_action_and_denies_unknown`, the retargeted `test_run_tool_code_nav_call_graph_sketch_smoke`, the `refactor_precheck` template assertions (which now also check `action`) and the legacy-ratchet baseline. See `docs/工具说明.md` / `docs/en/TOOLS.md`.

- **`get_current_time` / `calc` / `convert_units` removed from the registry**: three `ToolCategory::Basic` shims that kept arithmetic, time and unit conversion behind their own specs even though each had a better home — `date` is already on the `run_command` allowlist, and `python_snippet_run` / `run_command` cover the other two. The Legacy ratchet baseline drops **67 → 64** (64 → 61 without `archive-tools`), the `basic_network` shard loses three descriptions, and the `unit-tools` Cargo feature goes with them (`uom` dependency removed; `calc.rs` / `time.rs` / `unit_convert.rs` deleted). Two capabilities go with them and are named explicitly rather than glossed over: `calc`'s **`bc -l` arbitrary precision** (Python float division truncates differently) and `convert_units`'s **`uom` type safety**, including the decimal-vs-binary data distinction (`KB` vs `KiB`) — a hand-rolled conversion table gets temperature offsets and prefix chains wrong *silently*, since a wrong conversion raises no error. `get_current_time`'s `mode=calendar` month grid has no `run_command` equivalent either (`cal` is not allowlisted). Two follow-on consequences: (1) **`builtin_sync_default_inline_tools()` is now empty** — it contained exactly these two tools, so by default no `SyncDefault` tool skips `spawn_blocking`; the `tool_registry_sync_default_inline_tools` config key still overrides it; (2) `/health` no longer probes `bc` (`dep_bc` gone) and the `bc` install hint left `cli_missing_install_hint_for_base_name`. **Breaking**: any `allowed_tools` entry, agent-role list or workflow naming the three must drop them. Test fixtures that leaned on them as convenient tool names (`dispatch_tool_single_call_when_retry_disabled`, `dispatch_tool_retry_enabled_success_still_single_call`, `try_dispatch_meta_unknown_is_none`, `sync_default_inline_tools`, the dev-tag / schema / `known_tool_rejects_wrong_type` asserts, `tests/lib_smoke.rs`) were retargeted at `json_format` / `text_transform`, and the e2e scenario `orch_single_agent_tool` — which instructed the model to call `get_current_time` — was removed rather than pointed at a different tool. See `docs/工具说明.md` / `docs/en/TOOLS.md`.

- **The nine `schedule` tools are now `reminder` + `event`, and both finally count as write-effect tools**: `add_reminder` / `list_reminders` / `complete_reminder` / `delete_reminder` / `update_reminder` and `add_event` / `list_events` / `delete_event` / `update_event` shared two JSON files (`.crabmate/reminders.json` / `.crabmate/events.json`) and most of their field names, yet each carried its own `ToolSpec`. They are now two specs (`ReminderArgs` + `ReminderAction` = `list` / `add` / `update` / `delete` / `complete`; `EventArgs` + `EventAction` = `list` / `add` / `update` / `delete`), taking the Legacy ratchet baseline from **74 → 67** (71 → 64 without `archive-tools`). The nine existing implementations are **unchanged** — each still parses its original per-action DTO and the new dispatchers only adapt `action` → DTO — so the verified read/write flows are not rewritten; the cost is one extra JSON round-trip on tiny payloads. Required-field rules that used to live in the DTO alone (`add` needs a non-empty `title` / `start_at`; `update` / `delete` / `complete` need `id`) are now enforced in the dispatcher with actionable messages, since a union struct cannot express them per action. **These nine were also missing from `builtin_write_effect_tools()`** — a pre-existing defect that let `add` / `update` / `delete` / `complete` run as "read-only", so they were eligible for the parallel read-only batch and the same-turn dedup cache. `reminder` and `event` are now listed there, which means `list` loses its read-only treatment as well (the same trade-off `gh_pr` accepted for `checks`) — the alternative was per-action read-only tracking, deliberately **not** introduced. **Breaking**: `allowed_tools` entries, workflow `tool_name`s, agent-role lists and saved sessions naming any of the nine old tools must switch to `reminder` / `event` + `action`. Pinned by `reminder_action_dispatch_covers_all_five` / `event_action_dispatch_and_required_fields` plus the three pre-existing flow tests. See `docs/工具说明.md` / `docs/en/TOOLS.md`.

- **The three read-only background-job tools are now one `background_job` tool with an `action` selector, while `background_job_cancel` keeps its own tool**: `background_job_status` / `background_job_list` / `background_job_output` queried the same in-process `ToolJobRegistry` through the same `ToolJobsToolHost`, so the always-resend `tools` array carried `tool_job_id` / `cursor` / `limit` in three near-duplicate parameter objects. They are now one spec (`BackgroundJobArgs` + `BackgroundJobAction` = `status` / `list` / `output`), taking the Legacy ratchet baseline from **76 → 74** (73 → 71 without `archive-tools`). `background_job_cancel` is deliberately **not** folded in: it mutates job state and therefore sits in `builtin_write_effect_tools()`, so merging it would have dragged the three read-only actions out of the parallel read-only batch, read-only retry, `Ask`/`Plan` gating and read-only TTL cache — the same cost `gh_pr` accepted for `checks`. The tool-name consequence is handled: `builtin_dedup_cache_exempt_tools()` now exempts `background_job` instead of the three old names, without which same-turn re-queries would start hitting the read-only dedup cache and return stale job state. Sub-implementations, trim-then-reject on an empty `tool_job_id`, the `limit` default/clamp and the host-missing degradation text stay the same, with `status` / `output` now sharing one `require_job_id` helper. Two semantic details are worth calling out, both now spelled out in the tool description and `docs/工具说明.md`: fields irrelevant to the chosen `action` are **ignored** rather than rejected (the union struct keeps `deny_unknown_fields`, so unknown keys still fail, but e.g. `cursor` alongside `action=list` no longer errors), while `limit` keeps its `schemars(range(1..=100))` and is therefore range-checked for **every** action even though only `list` reads it — passing `limit` with `action=status` fails schema validation instead of being silently dropped. **Breaking**: any `allowed_tools` entry, workflow `tool_name`, agent-role list or saved session naming `background_job_status` / `background_job_list` / `background_job_output` must become `background_job` + `action`; `background_job_cancel` is unchanged. See `docs/工具说明.md` / `docs/en/TOOLS.md`.

- **`apply_patch` now previews on request, commits atomically, and never half-applies a multi-file patch**: it was the last write tool still doing a bare `std::fs::write` per file — and because it applied hunk by hunk, a 5-file patch that failed on the 3rd file had already written the first two (the only signal was a「补丁部分应用」line). It now runs in two phases: every hunk is first **planned** (read + `diffy::apply`, nothing written), and only if all of them succeed does anything hit disk — a partial failure now leaves the workspace byte-identical. New **`dry_run`** (default `false`, because the tool's name is "apply") returns the same unified-diff preview the other write tools give. Writes go through `file::write_bytes_with_revision_guard` (tmp → inherit metadata → `fsync` → revision check → `rename`), and a new optional **`base_revision`** gives single-file patches the same CAS as `modify_file` / `structured_patch` — passing it for a multi-file patch is a hard error rather than a silent no-op, since one revision cannot express several files' baselines. Deletes honour both knobs too (`dry_run` keeps the file, `base_revision` gates the removal). The signature changed from `(args, workspace_root, changelist)` to `(args, &ToolContext)` so the guard can reach the turn's revision binding; the hunk helpers were folded into `PatchApply` + `PlannedPatch` so no function takes more than 4 parameters. New tests in `patch/tests_write.rs` (dry_run keeps bytes, delete not removed, stale revision rejected, multi-file + `base_revision` rejected) and the partial-failure test now asserts nothing was written. - **`structured_patch` now commits through the shared write pipeline (optional CAS + atomic replace) and previews a unified diff**: it was the only **structured-data** write tool that rewrote a whole file with a bare `fs::write` — no revision check, no temp file, and a preview that reported `新文件大小: N 字节` instead of what would change. (`apply_patch` still writes with a bare `fs::write` too, but it is a patch-application tool with its own root-checked path resolution and typed errors; its gaps — no `dry_run`, no atomic replace — are separate work, not conflated here.) It now calls `file::write_bytes_with_revision_guard` (the same entry `modify_file`'s `full` mode uses): same-directory temp → inherit owner/permissions/xattrs → `fsync` → revision check → `rename`, so a concurrent reader never sees a truncated file and a `nlink > 1` target keeps its inode. New optional **`base_revision`** provides the CAS: pass the `revision` from a `read_file` output header and a stale file yields `错误[stale_revision]` with nothing written. It is deliberately **not** auto-bound to the turn's `read_file` (unlike line-mode edits) — key-path edits do not drift the way line numbers do, so requiring a baseline would break existing callers for no safety gain. Previews (`dry_run` omitted or `true`) now return the unified diff (`--- a/<path>` / `+++ b/<path>`, rendered by the same `text_diff::diff_unified` and byte-budgeted) instead of a byte count, and they honour an explicit `base_revision` too — a stale snapshot fails the preview rather than handing back a diff that looks safe. The diff is only built on the preview path, so a write does not pay for rendering it. Note the write still re-serializes the whole document (JSON → pretty, TOML/YAML regenerated without comments), which is why a previewed diff often looks like a full re-layout; that is now called out in `docs/工具说明.md` together with the advice to prefer `modify_file` / `search_replace` for comment-bearing configs. The write path also propagates the typed `错误[...]` codes on its first line instead of wrapping them as `写入失败: {e}`. Pinned by four tests in `structured_data_patch/tests_revision.rs`. See `docs/工具说明.md`.

- **`modify_file` guards collapsed into one `guard` object, and its description shrank ~4×**: the four flat guard parameters (`expect_content` / `expect_first_line` / `expect_last_line` / `expect_line_content`) were defined **twice** — once on `ModifyFileArgs`, once again inside `ModifyFileEditArgs` — with eight duplicated doc blocks and the mutual-exclusion rules restated in prose at each site. Preview tests that had been forced to pass `allow_stale_revision=true` dropped it, and `test_write_tools_default_to_preview_without_dry_run` now pins "preview works with no baseline". **`append_file` was the last write tool outside the knob** (`#[serde(default)]`, so it wrote when `dry_run` was omitted) — the one direction where the new mental model was unsafe: a caller who learned "omit `dry_run` → preview" would have silently written. It now defaults to `true` too, so all four write tools share one rule. The four scattered `dry_run` reads collapsed into `write_ops::dry_run_arg`, so a new dispatch branch cannot re-introduce an old default. `SearchReplaceArgs.confirm` / `StructuredPatchArgs.confirm` are marked deprecated in their schema doc. See `docs/工具说明.md`.

- **`modify_file` now defaults to preview (`dry_run=true`), and the three write tools share one write gate** — breaking for callers that relied on "omit `dry_run` and it writes". The old state had **two** separate inconsistencies: `modify_file` defaulted `dry_run=false` (wrote unless told otherwise) while `search_replace` / `structured_patch` defaulted `true`; and those two additionally demanded `confirm=true` on top of `dry_run=false`, a second lock that the model always supplied anyway — its only reliable effect was producing "silently didn't write" when forgotten (it happened to me mid-session). Now there is one rule: **omit `dry_run` and you get a preview; pass `dry_run=false` and it writes.** `confirm` is no longer checked by `search_replace` / `structured_patch` (fields kept so existing calls stay valid). ### Fixed

- **The `search_replace` tool-card line now spells the tool the way the registry does**: `SearchReplaceSummaryArgs::summary_line` hard-coded `search-replace{}: …`, while the tool itself is `search_replace` — so every client showed a hyphenated name the tool list never uses (`search_replace (preview): a.rs / "foo"`; previously `search-replace (preview): …`). No other summary line spells a tool name with a hyphen: the rest either use plain words (`read file:` / `delete directory:` / `chmod:`) or the registry name itself (`terminal_session exec …` / `gh api …`), so this was a typo rather than a convention. No protocol change — the field, its type and its semantics are untouched, and the client TUI's `-`/`_` normaliser simply becomes a no-op: it can be deleted on its own schedule, with no behaviour change either way (nothing in this repo keys on the hyphenated form), so no Client-repo change is required to ship this. Pinned by tests in `cm_tools::tools::tests` covering both the preview and the write form.

- **`run_command` tool-card summary no longer degrades to the placeholder for array-shaped commands**: `RunCommandSummaryArgs.command` was declared `String`, so a model that wrote the whole command as an array (`{"command":["git","status","-sb"]}`) made the struct fail to deserialize — the summary fell back to `tool: run_command`, and every client then had to re-parse the argument JSON to recover the command (the Web shell and the TUI each carried their own copy of that recovery, which is exactly how the two drifted apart). `command` is now a `serde_json::Value`: a string stays verbatim (it *is* the line to display, so quoting it would be wrong), an array becomes one token per element, and `args` is appended in both shapes — `{"command":["git"],"args":["status","-sb"]}` renders `git status -sb` as well. An empty command still yields `None`, leaving the placeholder decision and any last-resort rendering to the client (unchanged). Pinned by three tests in `cm_tools::tools::tests` (array command, array plus `args`, empty command).

- **Spurious `run_command` failures on multi-line invocations**: the tool echoes the raw argv after `命令：`, so a multi-line argument (`git commit -m "…" -m "…"`) makes that echo span dozens of lines. `strip_leading_command_invocation_line` drops only up to the first newline, so the "first line" used for status was really **message body**: `parse_exit_code` missed `退出码：0`, the parser fell back to the `失败` / `超时` keyword heuristic, and reported `ok=false` with `exit_code=null` **even though the command had exited 0** (seen on `git commit` whose body contained 「失败」). The exit code is now also read by scanning the header region up to the first `标准输出：` / `标准错误：` marker, so multi-line echoes still yield the real code; the scan only trusts outputs carrying those markers, so an `退出码：N` inside another tool's payload (e.g. a file returned by `read_file`) is never mistaken for status. Non-zero exits still fail. The parser moved to `cm_tools::tool_result::run_command` — `tool_result/mod.rs` had been sitting exactly at the 920-line cap, so any further edit there was blocked.

### Security

- **`AGENTS.md` symlink escape blocked**: that file's content is injected into `system` and sent to the model, so a workspace symlink pointing at an arbitrary local file (e.g. `/etc/passwd`) would have pulled it into the conversation. The loader now canonicalizes the path and **ignores** the file when it resolves outside the workspace root; symlinks pointing inside the workspace still work. Unix-only. See `docs/配置说明.md`.

- **Cleared the three RustSec vulnerabilities flagged by `cargo audit`**: bumped three transitive TLS crates to their fixed patch releases — **`rustls-webpki`** `0.103.15` → `0.103.16` (**RUSTSEC-2026-0382**, certificate verification may accept distrusted intermediates), **`webpki-roots`** `1.0.6` → `1.0.10` (**RUSTSEC-2026-0381**) and **`webpki-root-certs`** `1.0.6` → `1.0.10` (**RUSTSEC-2026-0383**) — the latter two because their bundled root sets still trusted distrusted emSign intermediates. All three live in the existing `rustls 0.23` graph, so this is a lockfile-only patch-level bump: no source, wire-protocol or config change. The five remaining `cargo audit` entries are upstream-blocked **`unmaintained`** warnings (`paste`, `term_size`, `zbus_names`, `zvariant`, `zvariant_derive`), which `cargo audit` reports as non-fatal and which stay documented as transitive.

### Added

- **`serve --yes` to bypass the command allowlist**: a new `serve` flag replaces `allowed_commands` with the allow-all sentinel **`["*"]`**, so **`run_command`** (and `terminal_session` first-frame `exec`) no longer validates the command name and runs any program. The sentinel is honored at the single host-side gate (`resolve_run_command_exec_path`), the approval layer (`cmd_missing_from_allowlist`, shell-wrap approval), and the peripheral consumers (`gh_allowed`, `error_output_playbook`, plugin/dynamic-tool validation, `doctor`), and is preserved across `POST /config/reload`. It is equivalent to **`CM_ALLOWED_COMMANDS=*`** and is intended **only** for fully trusted or already-isolated (container / dedicated host) environments; it does **not** disable workspace-external path approval or argument-safety checks. See `docs/命令行与路由.md` / `docs/工具说明.md` / `docs/配置说明.md`.

- **Background-job monitoring tools**: added two model-facing tools for the background tool-job lifecycle (design doc `docs/design/background_tool_jobs_contract.md` §9). **`background_job_output`** (read-only) incrementally pulls a job's output (`tail -f` semantics) via `tool_job_id` + optional `cursor` (the previous `next_cursor`), returning stdout/stderr deltas plus `next_cursor` and `eof`; it reuses the existing `ToolJobRegistry::poll_output` and is exempt from the same-turn read-only dedup cache (its output changes within a turn). **`background_job_cancel`** cancels a job (`queued` → `cancelled`, `running` sets the cancel flag, already-`cancelled` is idempotent success, other terminal states cannot be cancelled); it reuses `ToolJobRegistry::cancel`, is **termination** (not execution launch) so it does not violate the ADR's "no new execution-launching tool group" constraint, and is registered in `write_effect_tools` for auditing. Both are injected through `ToolJobsToolHost` (no allowlist approval). See `docs/工具说明.md` / `docs/en/TOOLS.md`.

- **`GET /tools/plugins/{file}` endpoint**: read-only single-file detail for a workspace dynamic tool definition (`<workspace>/plugins/{file}`), returning `file` / `name` / `description` / `valid` / `error` / `command_allowed` / `parameters` / `args` / `pass_args_json`. `{file}` must match `[A-Za-z0-9_-]+.json` (otherwise **400** `INVALID_PLUGIN_DEFINITION`); an unset workspace or a missing file returns **404** `PLUGIN_NOT_FOUND`. Closes the read-only tail of the tool-management API (design doc `docs/design/tool_management_api.md` §3.4). See `docs/命令行契约.md` / `docs/命令行与路由.md`.

- **Context-archive retention configuration**: two new `[agent]` keys make the cross-turn original-text archive (design doc `docs/design/context_window_compaction.md` §3.8 / §4.2) tunable. **`context_archive_max_rows_per_conversation`** (`CM_CONTEXT_ARCHIVE_MAX_ROWS_PER_CONVERSATION`, default **`256`**, `0` = unbounded) caps the per-conversation archived-prefix rows and drives the SQLite `prune` cascade; reclaiming an old prefix makes branch points older than the retained window fail to re-expand (the branch API returns an explicit error). **`context_archive_codec_min_bytes`** (`CM_CONTEXT_ARCHIVE_CODEC_MIN_BYTES`, default **`4096`**) is the archive-body codec threshold (below it `identity`, otherwise `gzip`). Both are hot-reloadable and validated (`0..=10_000_000` / `0..=4_194_304`). See `docs/配置说明.md` §会话持久与保留策略.

- **`/btw` LLM-summary toggle**: one new `[agent]` key, **`context_btw_summary_enabled`** (`CM_CONTEXT_BTW_SUMMARY_ENABLED`, default **`false`**), gates whether the off-the-record **`/btw`** side-question path (design doc `docs/design/context_window_compaction.md` §3.10 / §5.3.6) may make **one** optional LLM summary attempt while doing its read-only dry-run compaction. - **`GET /conversation/messages` can now include the archived original text**: a new optional query parameter **`include_archive`** (boolean, default **`false`**) makes the response carry an additional optional **`archive`** array with the conversation's already-archived (moved-out-of-canonical) original messages when set to `true` (design doc `docs/design/context_window_compaction.md` §5.3.4 C2). The field is omitted when empty (`skip_serializing_if`), so the default response body is byte-for-byte the same as before and old Clients are unaffected. ### Changed
- **Cancelled turns now persist their produced content**: when a Web stream turn is stopped (**`POST /chat/stream/{job_id}/cancel`**, or the SSE receiver drops while a cooperative cancel is pending — `cancelled_by_signal`), the partial output already produced in that turn (assistant text, `tool_calls`, completed `tool` results) is now **best-effort persisted** to the conversation store instead of being discarded, so the **next** turn's model context includes "what I already produced before the user interrupted". Two previously-leaking branches are covered: the `Ok` path (the agent had already merged the partial assistant and committed the derived view, but `stream_job_outcome_after_agent_turn` did `let _ = commit`) and the `Err`/`UserCancelled` path (the failed turn never wrote back). The interrupted path writes back **append-only** — no compaction, no archive, no `ConversationTurnGroup` derived view (`ModelContextView::append_current_turn_to`) — and completes a half-finished tool batch (`assistant(tool_calls=[A,B]) + tool(A)`) with placeholder `tool` messages so the persisted sequence stays legal (otherwise the next request would be rejected with an upstream **400**). Persistence reuses the existing CAS (`save_conversation_messages_if_revision`; `Conflict` is logged only), is skipped when the turn produced no visible assistant output, and **does not** change the SSE terminal semantics — the cancel path still emits only **`STREAM_CANCELLED`** with no `conversation_saved` / state snapshot / `stream_draining` and no long-term-memory async indexing. See `docs/SSE协议.md` / `docs/en/SSE_PROTOCOL.md` / `docs/design/context_window_compaction.md`.

- **Persist-time injection stripping now also drops execution-constraint ephemeral system messages**: the pre-persist / pre-structural-commit sanitize chain (design doc `docs/design/context_window_compaction.md` §3.7.1) is extracted into a single named helper **`strip_persist_injections`** (`src/chat_job_queue/stream_finish.rs`) and gains a fourth step — `retain(!is_execution_constraint_ephemeral_system)` — so any execution-constraint **system** injection that survives `outer_loop`'s per-turn `retain` is now **explicitly** removed before persistence instead of relying on that implicit side effect. **Behavior change**: previously such residue would have been persisted into `canonical`; the chain still **keeps** the baseline summary (`CRABMATE_CONTEXT_SUMMARY_NAME`) and the first-turn workspace profile (`CRABMATE_FIRST_TURN_WORKSPACE_CONTEXT_NAME`).
- **Raised the embedded default output/context budget for the shipped DeepSeek default**: `config/default_config.toml` now ships **`max_tokens = 16384`** (was **4096**) and **`llm_context_tokens = 262144`** (was **65536**, i.e. 256k), matching the real `deepseek-v4-flash` gateway (≈1M-token window, 384k max output, thinking on by default) instead of the old conservative "64k" placeholder. See `docs/design/run_loop_state_ownership.md` / `docs/design/client_contract_versioning.md`.

### Fixed
- **A cancelled turn can no longer poison the next request with an incomplete `tool_calls` batch**: when a Web stream turn is stopped while the model is still streaming a tool call, the persisted history could end with `assistant(tool_calls=…)` whose `arguments` were truncated and which had no `tool` response. Intermediate failures are **not** written to model context; only the final result is returned. `codebase_semantic_search` is hard-excluded (its `rebuild_index` writes workspace SQLite); `http_fetch` URLs that would require approval and external-path `read_dir` calls are skipped to avoid re-prompting.
- **Background tool job live output streaming**: `run_command` background jobs (`async:true`) expose **`GET /tools/jobs/{id}/output?cursor=`** incremental polling (`tail -f`): per-job bounded ring buffer (`seq`-monotonic items with `stdout`/`stderr`, `cursor` / `truncated` / `eof`), output not truncated by `command_max_output_len` during streaming, terminal tail trimmed to the output cap, ownership check identical to the status endpoint. New config `background_job_output_buffer_bytes` (default `262144`). Requires a matching **crabmate-client** build to show live output in the job bubble (old client ignores it; old `serve` falls back to status-only polling).

### Changed

- (none yet)

### Fixed

- **Explicit network-tool error codes**: `http_fetch` / `http_request` failures now carry first-line markers (`错误[code]：`) classified precisely — `http_timeout` (retryable), `http_network_error`, `http_body_read_error` — and `get_weather` / `web_search` map API failures to `weather_api_error` / `web_search_api_error`, instead of the coarse `*_failed` heuristic.

Workspace **`@rel.png` / `file:///rel.png`** skip text expansion and are inlined from that turn’s working directory. **`GET /uploads/{filename}`** uses the same auth as other protected APIs; cleanup skips files still referenced in the conversation store.

## [0.1.0] - 2026-08-08

First public **server** release tag (`v0.1.0`). Cargo package version was already `0.1.0`; this changelog marks the cut for GitHub Release / installable artifacts.

**Scope**: this repo is the Agent **server** (HTTP API, tools, SSE). At this tag the tree still included in-process **CLI/REPL/TUI**; those entries were **removed in D2.2** (see [0.3.0]). Official Web UI and desktop/Android shells live in [`crabmate-client`](https://github.com/noisystreet/crabmate-client) (path A, Phase 4.2 complete).

### Added

- OpenAI-compatible `chat/completions` client (DeepSeek, MiniMax, Zhipu GLM, Moonshot Kimi, Ollama, …) with streaming, retries, and tool calling.
- HTTP **`serve`**: `/chat`, `/chat/stream` (SSE / AG-UI), workspace APIs, conversation SQLite under `.crabmate/`, optional Web API Bearer.
- Built-in tool registry (`run_command` allowlist, file tools, fetch, cargo/npm stacks, workflows, optional MCP / Docker sandbox / fastembed via Cargo features).
- CLI: `serve`, `doctor`, `models` / `probe`, `save-session`, `mcp`, packaging helpers. Historical at this tag also: `repl`, `tui`, `chat` (removed in D2.2).
- CLI **`web-bearer status|set|clear`**: persist the Web API shared secret in the system keyring (same slot as Web Settings); **`serve`** falls back when TOML / **`CM_WEB_API_BEARER_TOKEN`** are empty. Prefer **`set --stdin`** / **`set --from-env`** / interactive hidden input to avoid putting the secret on argv.
- Client contract versioning gates (`client-contract-v*`) and CI smoke for SSE / OpenAPI / consumer pins.
- Release packaging: `make package` → server-only **tar.gz** + **`.deb`**; **systemd** unit (`crabmate.service`), `/etc/crabmate/config.toml` + `config/prompts/`, env example (`KEY=value` only).
- GitHub Actions **Release** workflow (`.github/workflows/release.yml`): tag `vX.Y.Z` (or `vX.Y.Z-rc.N`) → `make package` + GitHub Release with tar.gz/deb; notes from this file’s core `X.Y.Z` section; re-run updates the same Release.
- Default English [`README.md`](README.md) with Chinese companion [`README.zh.md`](README.zh.md).

### Changed

- Path A: removed in-repo `frontend/`, desktop/mobile shells, and Playwright ownership from this repo; document pointers target Client.
- CI package job: server-only artifacts; test job avoids full `cargo clean` (clears incremental only when free disk is low).

- Deb package smoke grep paths aligned with `dpkg-deb -c` output (`./usr/bin/…`).

### Known limitations (0.1.0)

- **Trusted workspace** model: `run_command` allowlist includes powerful tools (`bash`, `git`, `cargo`, …). Not a multi-tenant SaaS.

- Default Cargo features include **`mcp`** (with `web`); in-process **`repl`/`tui` features removed** (D2.2). Heavy options such as **`fastembed`** remain opt-in.
- Systemd service user has a **minimal `PATH`**; extend via `/etc/crabmate/crabmate.env` for host toolchains. Bypass HTTP proxies for `127.0.0.1` when probing locally.
- Compatibility-layer shrink items **B2–B4**, full unwrap audits, and agent benchmarks remain backlog ([`docs/待办清单.md`](docs/待办清单.md)).
