## [Unreleased]

### Added

- **`crabmatectl` gained `add` / `remove` / `disable` / `enable`: the declaration is editable from the shell again**: `instances.toml` could only be changed by hand or through the `supervise --socket` control plane, so a shell user had no way to add or retire a lane without an editor. The four subcommands reuse the socket's exact field surface (`name` / `workspace` / `profile` / `port` / `enabled`; `remove` / `disable` / `enable` take only `name`) and — deliberately — the same **verbs**, so the CLI, the socket `op` and the file keys stop being three vocabularies for one concept (the earlier candidate name `decl` was rejected for exactly that reason). They **write configuration only**: nothing starts or stops, `add` needs a later `up` or a converging `supervise`, `disable` waits for the resident `supervise --watch` to stop the process, and `down` remains the immediate killer. `enable` still clears the `desired_state = stopped` marker that `down` leaves behind: the socket's `enable` already did, so letting the CLI skip it would give one command two behaviours depending on the channel — and the lane would be skipped forever while the declaration said `enabled = true`. `env` and `config` are **not** accepted, for the same reasons the socket refuses them (`config` would re-open arbitrary config paths; `env` in an idempotent `add` only invites「为什么我给的变量没生效」); both stay hand-written, and `add` therefore also cannot create a `workspace`-less pending lane — that stays a file-only affordance, consistent with `crabmatectl up <name>` already rejecting a missing workspace. Implementation is one copy, not two: `control.rs`'s `add` / `remove` / `set_decl_enabled` were extracted into `src/cm_ctl/decl.rs` returning `Result<_, CtlError>`, with the socket adapting that into its existing JSON (`created` / `changed` / `cleared_down` / `note` / `warning` all unchanged, so the socket's own tests now guard the CLI path as well) and the CLI adapting it into human output via `render` — which also spells out that only the declaration changed and who acts on it. The socket `note` text loses a typo along the way（「再无 add」→「再 add」). Docs: `docs/命令行与路由.md` (a CLI / socket / hand-written split table plus the `up`-vs-`add` and `down`-vs-`disable` distinction), `docs/开发文档.md`, and a regenerated `man/crabmatectl.1` — this is the first **structural** subcommand addition, and unlike adding a flag it does change the man page. Tests: `decl` primitives (idempotent `add` that preserves a hand-written `env`, `bad_workspace` / `bad_name` rejection with no file written, idempotent `remove`, `disable` preserving `profile` + `env`, `enable` clearing the down marker, retry-safe `changed: false`) plus the CLI dispatch (`--enabled` defaults to true, `--instances-file` is honoured, `env` / `config` never written). Refs #1215.
- **New tool `background_job_wait`: wait for a background job instead of polling it across turns**: `run_command` / `cargo_test` / `pytest_run` could already hand a long job to the queue with `async: true`, but the only way to learn it had finished was for the model to call `background_job action=status` again and again — each round a full LLM round-trip, which the issue that requested this (#1194) measured as the dominant cost of using background jobs at all. The new tool blocks **inside one tool call** until a condition holds: `until=exit` (default) returns when the job reaches a terminal state, `until=output_matches` returns as soon as a **substring** (not a regex, ≤256 bytes) appears in the retained output window — the dev-server case, where `listening on` arrives minutes before the process exits. `timeout_secs` is clamped to 1–600 (default 60) and **never cancels the job**: a timeout only ends the wait, leaving the job `queued` / `running`, so the caller can wait again or fall back to `background_job action=output`; the response deliberately keeps「等待结果」and「任务状态」apart, because a job that ended in `timed_out` and a wait that timed out are different facts that used to collide in one word. Three decisions worth recording. (1) **It is a separate tool name, not a fourth `background_job` action**: blocking tens of seconds would break the identity the three existing actions rely on — they are in the parallel read-only batch and they are dedup-cacheable, and a cached second wait on the same id would return the first wait's answer forever. The new name is therefore added to `builtin_parallel_sync_denied_exact` (out of the parallel read batch) and `builtin_dedup_cache_exempt_tools` (out of the same-turn dedup cache) while staying **out of** `write_effect_tools`, since a timed-out wait changes nothing. The read-only TTL cache needed no change: `serial_try_ttl_run_command_cache_hit` only ever applies to `run_command`. (2) **Waiting is event driven, not polled**: the registry's lock is a plain `std::sync::Mutex` and tool bodies already run under `spawn_blocking`, so a `Condvar::wait_timeout` is the right primitive — the condition check and the wait happen under the same lock, so a wake cannot be lost, and `notify_all` fires on every output push (not only on terminal states, or `output_matches` would never wake), on `complete`, on both `cancel` branches, on `try_start`, and when `cleanup` removes an entry. Matching scans only the newly appended blocks, carrying a `len(pattern)-1` byte tail so a substring split across two pushes still matches — matching cost tracks new output, not buffer size. (3) **The inner wall clock reserves one second under `command_exec command_timeout_secs`**: `SyncDefault` tools are wrapped in an outer `tokio::time::timeout` carrying that same value, so without the reserve a 600 s wait would be cut by the outer timer and the model would receive the generic「工具执行超时」instead of the structured wait result. Docs: `docs/工具说明.md` / `docs/en/TOOLS.md` (new tool + `run_command` `async` note), `docs/配置说明.md` (no new config key, wall-clock reservation), and `docs/design/background_tool_jobs_contract.md` §10 (why a separate tool, the `Condvar` design, the reserve, the four `notify_all` points). Tests: `registry_wait_tests` (terminal returns immediately, `output_matches` wakes without waiting out the timeout, substring across two pushes, timeout leaves the job untouched, `queued`→`running`→terminal wake, cancel wake, two consecutive waits on the same id both observe new progress, `NotFound`/`Expired`, 20× complete-vs-wait race), host-level wording, and tool-level clamping / `deny_unknown_fields` / no-host degradation.
- **`crabmatectl restart --grace <SECS>`: the "gentle remedy" is no longer forced into `SIGKILL`**: `restart` hard-coded the 10 s default grace while `serve` measures **~30 s** to exit after `SIGTERM`, so the exact command `docs/命令行与路由.md` prescribes for "profile changed, needs a restart" reliably ended in `SIGKILL` — killing an instance mid-shutdown precisely in the flow that is supposed to be the polite one, with no way to widen the window. The flag reuses the knob `down --timeout` and `supervise --grace` already expose (same meaning: grace before `SIGKILL`), so no new semantics were invented; the readiness wait stays on `--timeout`. `docs/命令行与路由.md` now names both widenings instead of only `down`'s.

### Fixed

- **`crabmatectl` no longer deletes or overwrites the record of a process that is still running**: `Observed::Stale` (`src/cm_ctl/probe.rs`) merges two opposite situations — a reused PID pointing at an unrelated process, and *our* serve still alive but not answering on its port — and both `prune` and `up` acted on that single verdict. `prune` therefore removed `<name>.json` while the process kept running, and `up` overwrote the record with the pid of a newly spawned process (which then failed on the instance directory's `.serve.lock`), leaving the original serve alive with nobody able to address it: `down` answered「实例不存在」, `ls` did not list it, `supervise` would not reclaim it. That is the orphan the macOS platform gate (`cm_ctl::PLATFORM_SUPPORTED`) exists to prevent, arriving through a different door. The predicate is now `pid_alive && identity.is_match()` (`Probe::process_is_live_and_ours`) — the same facts `down` already trusts — and it lives in a new `src/cm_ctl/guard.rs` shared by both call sites: `prune` skips such records by default and prints the reason per entry (`prune --force` still clears them, for the case where `down` cannot stop that process and the operator chooses to abandon it), while `up` / `restart` refuse with `instance_already_live` and point at the next step for the observed state (`starting` means a start is in flight — check `status`; anything else means `down`) instead of overwriting. That refusal shares **exit code 2** with `port_in_use` through a new `CtlError::conflict`, because for a caller both mean the same thing — *retrying right now is pointless* — and splitting them across 1 and 2 would force a script to test two codes to recognise it (`identity_mismatch` deliberately stays on `general`: the record is untrustworthy, not occupied, and the remedy is manual inspection). The check runs before port selection **and** again inside the state lock, because another ctl could start an instance in between. Records whose identity does *not* match stay prunable — clearing those is exactly what that branch is for — which is why `prune_still_removes_identity_mismatch` sits next to the two new cases. Tests drive a real substituted process (`sh -c 'sleep 30; :' serve`, whose cmdline carries the standalone `serve` token `identity::verify` looks for) and assert behaviour, not just the error code: the refused `prune` must leave the record in place, and the refused `up` must not rewrite it. Docs: `docs/命令行与路由.md` → 本地多实例（关键语义 + 已知限制）。Refs #1211.
- **`background_job_wait` review pass: no silently-wrong waits, no idling waiters**: four defects found by reviewing the new tool before merge. (1) **`output_matches` without `until` silently waited for exit.** The most natural call — “wait until the log says `listening on`” — sent only `output_matches`, and because `until` defaulted to `exit` the pattern was dropped and the call blocked on a process that (for a dev server) never exits, burning the full timeout and then reporting a timeout the caller never asked for. A non-empty `output_matches` now **infers** `until=output_matches`; a blank pattern still means `exit`. (2) **A cancelled job left the waiter idling.** `cancel` sets `cancel_requested` on a `running` job but leaves the record non-terminal (the worker lands the terminal state), and the wait condition only looked at terminal states — so a user turn stop (or `background_job_cancel`) released a waiter only when the worker unwound, or never before the deadline, holding a blocking thread for up to `timeout_secs`. The condition now includes the cancel flag and returns a distinct `CancelRequested` outcome, whose body says the wait ended early instead of pretending to be a timeout; the check order is terminal → match → cancel, so a substring already present in the log is still reported as a hit rather than as a cancellation. (3) **`WaitOutcome::TimedOut` renamed to `WaitOutcome::DeadlineReached`** — sharing the name of `JobStatus::TimedOut` reintroduced, inside the code, exactly the confusion the result body was written to avoid. (4) **One record snapshot instead of two.** The wait body used to render the head from the wait outcome and then re-read the record through `status`, so a record expiring between the two reads produced 「已到终态」 and 「已过保留时长」 in the same reply; both paths now share `render_job_record`. Alongside those, the seam scan no longer builds a block-sized temporary `String` while holding the registry lock (it searches the block in place and then only the `len-1` byte bridge, snapped to char boundaries), since the worker's `push_output` needs that same lock and a chunk can approach `output_buffer_bytes`. The tool is also added to `builtin_retry_denied`: a wait's duration *is* its budget, so transparent retries would double the wall clock and eat the one-second reserve that keeps the outer timer from firing first. Docs (`docs/design/background_tool_jobs_contract.md` §10.2–§10.4, `docs/工具说明.md`, `docs/en/TOOLS.md`) spell out the inference rule, the exit-condition order and the early cancel return. Tests added: `output_matches` inference and its blank-pattern counterpart, a multibyte pattern split across two pushes (the new bridge code must not panic on a non-char boundary), hit-wins-over-pending-cancel, `running`-cancel releasing the waiter immediately, and the host-level 「已请求取消」 wording.
- **`glob_files` and `search_in_files` were never treated as redundant read-only probes**: `READONLY_PROBE_TOOL_NAMES` listed `list_dir` / `glob` / `search` — three names that have never been real tools (cleaned up in #1155) — so the list read like six entries while only three were live (`read_file` / `read_dir` / `list_tree`). Neither real search tool had an entry of its own, so once the active goal already had completion evidence a `glob_files` / `search_in_files` call was *not* suppressed and the turn ran one more search instead of stopping, while the strictly weaker `list_tree` was. Both are now in the list (as `crate::cm_names::*`), pinned by a new `redundant_tools` golden row (`readonly_redundant_glob_probe` in `fixtures/turn_completion_golden.jsonl`) and by `completed_gate_marks_search_family_probe_tools_redundant`; dropping either constant makes the golden fail with `tools_not_redundant`. Refs #1204.

- **`crabmatectl` claimed macOS support while its process management silently misread every instance**: identity and liveness (`boot_id` / `pid_start_ticks` / `cmdline` / `pid_alive`) all read `procfs`, and `src/cm_ctl` had no platform gate — so on macOS `pid_alive` was permanently `false`. That value is not merely optimistic, it inverted the meaning of `down`: `down_record` filters on `identity::pid_alive`, so the process was never signalled, the record was rewritten as `stopped` with `pid` cleared, and the command reported「未在运行（无需停止）」 while `serve` kept running as an orphan nobody could address afterwards. `ls` reported every lane as `stopped` and `--restart on-failure` treated that as a crash, starting one more `serve` per sweep. The root cause is conceptual: "no answer from procfs" was being expressed as "the process is dead". `cm_ctl::PLATFORM_SUPPORTED` (`cfg!(target_os = "linux")`) is now checked at the single entry point `cm_ctl::run`, rejecting everything else with `platform_unsupported` before any state file is read or written; the binary's `about`, module docs, `README.md`, `docs/命令行与路由.md`, `docs/开发文档.md`, `AGENTS.md` and the regenerated `man/crabmatectl.1` said "Unix" and now say "Linux" with the reason attached. A real macOS port (start time via `proc_pidinfo`, liveness via `kill(pid, 0)`) is deliberately **not** part of this entry — it needs a decision, not a side effect.

- **`crabmatectl restart` silently dropped `--yes`, turning「跳过白名单」into「白名单生效」**: `ops::restart` rebuilt its launch spec from the state record — which is the right source, since it is the only thing that survives a ctl restart — but the record had no `yes` field and the call site passed `yes: false` unconditionally. An instance started with `crabmatectl up --yes` therefore came back, after any `restart`, with the command allowlist enforced again: a permission **narrowing**, but also a different instance than the one the user asked to restart, announced by nothing except "the tools suddenly stopped working". `InstanceRecord` gained `yes` (`#[serde(default)]`, so existing records on disk read back as `false` — the pre-fix behaviour), `up` / `run` write it, `restart` restores it, `supervise` keeps passing `false` (its own comment already forbids `--yes` from the declaration side), and `status` prints it — as do `ls --json` / `status --json`, since a client that only sees the JSON would otherwise have to read the state file behind the public contract — so the answer does not require digging through shell history. `fixtures/ctl_contract.json` gained `yes` in `record_fields` **and** in `ls_row` / `status_row` — the deliberate review step that keeps `crabmate-client` from discovering the field by accident.

- **Resetting a bound workspace is no longer misread as "a different workspace"**: the one-workspace-per-instance gate compared `!raw.is_empty() && already == raw`, so the empty path counted as *different* — once an instance was bound to `/a`, `POST /workspace {"path":""}` answered `409 WORKSPACE_ALREADY_SET` instead of resetting. That closed the escape hatch `docs/design/ctl_workspace_unset.md` §3.1 spells out (`Some(x) --{path:""}--> Some("")`) and made "switch workspace" impossible in practice: the client TUI's `/workspace off` (which maps `off` / `default` to an empty path) failed first, so the second step could never run. The empty path is now outside the gate — an idempotent replay of the *same* path and the 409 for a *different* path are unchanged — and the 409 message names the next step (reset first, or start another instance). Pinned by `web::workspace::handlers_workspace_set_http_tests::workspace_set_is_one_bind_per_instance`; `docs/命令行与路由.md` now documents the three outcomes. Refs #1183.

- **`crabmatectl up --port` 撞上已被占用的端口时报「已就绪」，且 `base_url` 指向别人的进程**: `up b --port 8080` 在 8080 已被实例 `a` 监听时会「成功」，写出 `state: ready` 的记录并把 `base_url` 写成 `http://127.0.0.1:8080/` —— 和 `a` **一模一样**。根因在 `readiness::wait_tcp`：它把「我 spawn 的 pid 还活着」和「这个地址能连上」当作两件独立的事来检查，端口被别人占着时 `connect` 连到的是**别人**，于是判定自己的实例就绪。后果不是显示错误而是数据串台：客户端连 `b` 全落到 `a` 上，两个 lane 共用一份会话库，正是 `crabmatectl` 每实例独立 cwd / 会话库的初衷被绕过；同时 `b` 的 serve 还活着但没监听，被记成健康后连 `supervise --restart on-failure` 也不会去救。现在显式 `--port` 在 spawn 之前先检查 `127.0.0.1:PORT` 是否已被监听，占用则报 `port_in_use`（退出码 2）并指出端口号，不进 readiness 等待。auto 分配不受影响（端口池本就跳过占用，其 TOCTOU 窗口仍由 `port_race` 顺延兜住）。新增单测与真进程集成测试各一条，后者钉的是**行为**而不只是错误码：失败的 `up` 不得留下任何记录。已把修复临时短路复验过——测试会如期报「端口被占用时 up 应失败」。见 `docs/命令行与路由.md` → 关键语义第 9 条。

- **A `crabmatectl up` whose readiness wait times out no longer parks the instance in `starting`**: on timeout `up` used to leave the child alive and keep `state: starting`, writing only a `last_error`. That combination is a dead end, and the reason is structural rather than cosmetic: `probe::observe` maps "`starting` + process alive + port closed" to `Observed::Starting`, while `restart::is_failure` only accepts `stopped` / `failed` / `stale` — so `supervise --restart on-failure` skipped the instance on **every** sweep, and it was neither retried nor reclaimed (exactly the "`starting` never self-heals" gap recorded in #1177 / #1180). Clients saw an ambiguous `starting` plus a non-empty `last_error` and could not tell "still booting" from "gave up". `#1163`'s own semantics table already said the opposite of the code ("timeout → `failed` + `last_error`, reclaim the process just started"), so the code moved: the timeout path now terminates the child's **process group** (`signal::terminate`, `SIGTERM` → grace → `SIGKILL`), clears `pid` / `pgid` / `base_url`, and writes `state: failed` with a readable `last_error` (pid and log path, plus a note when `SIGKILL` was needed or reclamation itself failed). A slow `serve` therefore either becomes `ready` or becomes an explicit `failed` that the backoff sweep can pick up, instead of lingering in a state nothing acts on. See `docs/命令行与路由.md` → 关键语义第 10 条.

- **`enable` on an instance whose declaration was already `enabled = true` answered `ok` and converged nothing**: the socket response's second value — "re-converge now" — was `changed` from `instances::set_enabled`, which only tracks the `enabled` field. `enable` *also* clears the `desired_state = stopped` marker a `down` leaves behind (without it `supervise` skips the instance forever), and that is a separate write, so the two disagreed: a client retrying `enable` — the obvious way to bring back a lane someone stopped with `crabmatectl down` — got `ok / changed:false / cleared_down:true` while no convergence ran at all. With the default `--restart never` and `--watch` following only the declaration fingerprint (a `desired_state` change is not part of it), the instance then stayed down indefinitely while the client showed it as running. The convergence flag is now `changed || cleared_down`, pinned by `enable_on_already_enabled_but_downed_instance_reconverges` — the earlier test could not reach this case because it went through a real `disable` first, so `changed` was always true there. Three doc comments and the `--socket` `--help` text also still listed `add` / `remove` / `list` only; they now name `disable` / `enable`.

### Changed

- **`search_replace` no longer replaces every occurrence by default — an ambiguous `search` is now refused instead of silently rewriting the file** (*breaking for callers that relied on "omit `max_replacements` → replace all"*): the old code read `max_replacements.unwrap_or(0)`, collapsing **"not stated"** and **"unlimited"** into the same value, so a one-line intent like "change `let x = 1;`" quietly rewrote every occurrence — and the success body only said「已替换 N 处匹配」, which the caller (usually the model) read as confirmation that the *one* edit landed. The tool description made it worse by mentioning `max_replacements` only as「可限制最大替换次数」, an optional optimization rather than a warning, and `dry_run`'s `true` default was no defence because callers pass `dry_run=false` in the same call and never see the preview. The default is now inverted: **omitting both `max_replacements` and `replace_all` means the anchor must match exactly once**; multiple hits are rejected with `invalid_args` (nothing written) and the body lists each hit's line number and trimmed text plus two concrete ways forward (tighten the anchor, or declare the scope). Explicit forms are unchanged and now named: `max_replacements=N` means "first N", while `max_replacements=0` — kept as the historical escape hatch — and the new **`replace_all: true`** both mean "every match"; supplying a non-zero `max_replacements` together with `replace_all=true` is a hard error rather than a silent precedence rule. Three further defects in the same code path were fixed while it was open, all found while writing the tests: (1) **`max_replacements > 0` re-scanned the mutated string**, so the loop's next `find` could hit text the previous iteration had just inserted (`"aXa"` with `a → aa` yielded `"aaaXa"`, leaving the second original `a` untouched) and each iteration rebuilt the whole string with `format!` (quadratic); replacement now walks the **original** text via `str::replacen` / `Regex::replacen`, which also keeps the regex crate's `$1` / `${name}` expansion intact (a hand-rolled splice would have broken capture references). (2) **The dry-run preview compared lines by index** (`zip`), so any replacement that changed the line count made every following line look changed and burned the 20-line cap — it now returns the same unified diff the write path renders. (3) **The write was non-atomic and had no CAS**: `write_bytes_under_root` is `open` + `write_all` (truncating), so a crash mid-write left a truncated file, and unlike `modify_file` / `apply_patch` there was no revision ticket. It now commits through `file::write_bytes_with_revision_guard` (tmp → inherit metadata → `fsync` → revision check → `rename`) and accepts an optional **`base_revision`**. The turn's `read_file` binding is honoured when it exists, but **is deliberately not required** — text anchoring does not depend on a line-number snapshot, and this tool is exactly what `modify_file`'s `missing_revision_baseline` message recommends as the way out, so requiring a baseline here would contradict its own advice. Multi-site writes now lead with `⚠ 多处替换` plus the hit line numbers, and `search` validation uses `is_empty()` rather than `trim().is_empty()` so whitespace-only anchors (`"\n\n"` to collapse blank lines, an indentation run) stay usable. **Migration**: add `"replace_all":true` (or `"max_replacements":0`) to any call that genuinely wants every match; otherwise the anchor now has to be unique. Pinned by nine new tests in `file::mutate` (ambiguous rejection with line numbers, both "all" forms, first-N not re-hitting inserted text, regex `$1` under a limit, scope conflict, whitespace-only anchor, unified-diff preview, stale `base_revision`) plus `search_replace_ambiguous_match_is_invalid_input_and_does_not_write` in `tests_typed_write_ops.rs`. See `docs/工具说明.md` / `docs/en/TOOLS.md`.

- **`POST /workspace` refuses to replace a workspace the instance is already bound to** (409 `WORKSPACE_ALREADY_SET`): the endpoint used to overwrite `workspace_override` on every call, so one `serve` process could serve two projects over its lifetime — and the second client inherited a running agent whose tools were pointed at a directory it never chose. `#1183` settles the model as **one workspace per instance**: a second *different* path is a 409 that names the current binding and says to start another instance, while re-sending the *same* path is an idempotent `200` (no runtime re-sync). The nuance that keeps this from being a breaking change for existing deployments: `Some("")` — "no `--workspace` given, use the configured default directory" — is **not** treated as bound, so the Web UI's first directory pick still works as before. Switching workspaces still has an explicit escape hatch (`POST /workspace` with an empty path resets), but it is no longer reachable by accident. Implemented in `set_workspace_from_raw_path`; `apply_workspace_override` (the internal path used by config reload and startup) is deliberately left unfiltered — it must be able to (re)establish the initial value. The `WORKSPACE_NOT_SET` gate on tool calls landed in a separate slice — see the `Added` entry below, which closes the gap this paragraph originally recorded.

### Added

- **A pending workspace now refuses tools instead of silently using the configured default directory** (`WORKSPACE_NOT_SET`, closing the gate #1183 describes): `serve --workspace-unset` starts an instance with `workspace_override: None`, but the tool boundary used to fall back to `command_exec.run_command_working_dir` anyway — so an instance whose client had not picked a directory ran commands and edited files in a directory the user never chose. Every `SyncDefault` tool now answers `WORKSPACE_NOT_SET` with an actionable hint (set the workspace in the panel, or `POST /workspace`); the same gate covers `run_command`, `terminal_session`, dynamic tools, the workflow node executor and `@` / `file://` references inside a chat message. Three boundaries are deliberate. **Only `SyncDefault` tools are gated**: egress tools (`http_fetch` / `web_search`) stay usable while pending, because they never touch the local tree and refusing them would shrink the capability surface with no safety gain (`execute_dispatch_body.inc.rs`). **`Some("")` is not pending**: an explicit "use the configured default" — a plain `serve` with no `--workspace` — keeps working, which is the control case that stops a CLI-only install from breaking. **The gate reads `workspace_is_set`, not the directory string**, so an empty path can never be confused with "unset". The switch is **opt-in**: `never` is the default and behaves byte-for-byte like before, because a supervisor that silently resurrects processes is a capability with a real cost and has to be asked for, exactly like `--yes`. Four boundaries are load-bearing. **The trigger set is explicit** (`stopped` / `failed` / `stale`) and `starting` is deliberately excluded — that is the intermediate state of a boot, `up`'s own readiness wait is its judge, and sweeping it would turn "slow start" into "crash". **The judgement is reused, not re-written**: a sweep runs the read-only `plan` and executes only its `Start` steps (`Running` clears the backoff, `Stop` / `Skipped` are never executed), so reclamation stays owned by declaration changes instead of quietly becoming "kill something every 30 s", and the second definition of "unhealthy" cannot drift from the first. **The backoff is persisted, not in memory** (`restart_attempts` / `next_restart_at`, additive record fields): a ctl restart must not hand a crash-looping instance a free immediate retry; the curve is `min(initial × 2^(n-1), max)` (5 s → 10 s → … capped at 300 s) with no attempt ceiling — a supervisor that gives up silently is worse than one that keeps trying, and the failure stays readable through `status`. **Failures are booked too**, otherwise an instance that can never start is retried on every sweep and the backoff does not exist in practice. Health sweeps run on their own cadence (`--health-interval`, default 30 s) rather than per declaration poll (1 s), because the latter only stats and reads a file while the former opens a TCP connection per instance; attempts blocked by the backoff stay silent (the record shows `next_restart_at`), so a crash loop does not print the same line every 30 s. - **`crabmatectl supervise` profiles: a preset menu instead of arbitrary `--config` paths**: instances could name a `config` file, which is unusable from a browser or phone (they cannot see the server's filesystem) and unbounded in principle (naming an arbitrary path means loading arbitrary TOML into a child process). `profiles.toml` turns that into a menu: the declaration side defines `[profiles.<name>]` once, instances only write `profile = "<name>"`, and `profile` + `config` together is rejected (`profile_and_config_conflict`) rather than silently preferring one. Fields are a fixed allowlist mapped onto existing `serve` capabilities — `config` → `--config`, `allowed_commands` → `CM_ALLOWED_COMMANDS`, `permission_level` → `CM_PERMISSION_LEVEL`, `llm_model` / `llm_api_base` → `CM_LLM_MODEL` / `CM_LLM_API_BASE`, `no_tools` → `--no-tools`, plus an `env` table — so no new HTTP contract is introduced. Merge order is ctl default → profile-derived keys → `profile.env` → `instance.env`, the last one winning. Four boundaries are load-bearing. **`workspace` and `yes` are permanently forbidden inside a profile**: `workspace` may only come from the instance (where `preflight` checks it against the child's `workspace_allowed_roots`), and allow-all must be an instance-level explicit decision — which also means `allowed_commands = ["*"]` is rejected, since it is `--yes` wearing a different hat. **`profiles.toml` gets the same `0600` gate as `instances.toml`** (`profiles_file_insecure`), because it decides which commands and which permission level a child gets; the check was extracted into `paths::check_private_file` so the two files cannot drift apart. **`CM_*` is a four-key allowlist, not a prefix**: passing a `CM_` prefix through would let a declaration inject `CM_SERVE_DISABLE_INSTANCE_LOCK` and dismantle instance isolation, so only the four keys above are allowed, all other `CM_*` / `API_KEY` / `*_TOKEN` / `*_SECRET` names keep failing with `forbidden_env`. **`permission_level` values are validated** (`chat` / `read` / `workspace` / `approved` / `unrestricted`) so a plausible-looking `readonly` fails loudly instead of being ignored. Changing a profile never hot-reloads a running instance: the state record now keeps a **fingerprint** of the effective profile (`config` + `no_tools` + the sorted env), not just its name, because editing `allowed_commands` / `permission_level` / `env` leaves the name untouched while changing exactly the capabilities that matter — a name-only check would report `ready` forever while the old permission set stayed in effect (this was caught by an end-to-end run, not by a unit test). Convergence then plans a restart that names the old and new profile, `restart` re-resolves the profile against the current file (dropping `--no-tools` or `allowed_commands` on restart would quietly widen an instance's permissions), and `status` shows `profile` (declared) next to `profile_in_use` (actual) with a hint when they differ. - **`crabmatectl supervise --watch`: declarations go live without a restart**: the one-shot convergence above needed an external scheduler to notice an edited `instances.toml`, which made "add a lane from the UI" a two-system dance. `--watch` polls the declaration (default 1 s, `--interval` adjustable) and re-converges whenever it changes. Polling rather than inotify is deliberate and matches `logs -f`: inotify is unreliable on container overlayfs, where bind-mounted files also miss `IN_MODIFY`. The fingerprint is **content plus permission bits**, and that second half is the load-bearing part: `chmod 600` fixes a `0644` declaration without changing a byte of it, so a content-only fingerprint would leave the watcher permanently stuck in "paused" with no way to observe the repair. When the declaration is unusable — too-wide permissions, foreign owner, TOML syntax error, or missing — convergence **pauses and warns** instead of exiting: editors invalidate files mid-save, and quitting a resident process over a half-written TOML is worse than pausing. Nothing is started from a broken declaration either, since "launch processes listed in a file I could not fully validate" is strictly worse than "launch nothing". The pause is observable (one `WARN` per distinct state, so a stable error does not spam every second) and self-healing (fix the file, the fingerprint changes, convergence resumes) — both paths are pinned by unit tests plus an end-to-end run that only widens permissions and changes no content. `--watch` and `--dry-run` are mutually exclusive (`conflicting_flags`). - **`apply_patch` now previews on request, commits atomically, and never half-applies a multi-file patch**: it was the last write tool still doing a bare `std::fs::write` per file — and because it applied hunk by hunk, a 5-file patch that failed on the 3rd file had already written the first two (the only signal was a「补丁部分应用」line). It now runs in two phases: every hunk is first **planned** (read + `diffy::apply`, nothing written), and only if all of them succeed does anything hit disk — a partial failure now leaves the workspace byte-identical. New **`dry_run`** (default `false`, because the tool's name is "apply") returns the same unified-diff preview the other write tools give. Writes go through `file::write_bytes_with_revision_guard` (tmp → inherit metadata → `fsync` → revision check → `rename`), and a new optional **`base_revision`** gives single-file patches the same CAS as `modify_file` / `structured_patch` — passing it for a multi-file patch is a hard error rather than a silent no-op, since one revision cannot express several files' baselines. Deletes honour both knobs too (`dry_run` keeps the file, `base_revision` gates the removal). The signature changed from `(args, workspace_root, changelist)` to `(args, &ToolContext)` so the guard can reach the turn's revision binding; the hunk helpers were folded into `PatchApply` + `PlannedPatch` so no function takes more than 4 parameters. New tests in `patch/tests_write.rs` (dry_run keeps bytes, delete not removed, stale revision rejected, multi-file + `base_revision` rejected) and the partial-failure test now asserts nothing was written. See `docs/工具说明.md`.
- **Three aggregate quality-check tools removed (`ci_pipeline_local` / `quality_workspace` / `release_ready_check`)**: the family existed to chain `cargo fmt` / `clippy` / `test` / frontend lint / ruff / pytest / mypy / `cargo audit` / `cargo deny` / worktree-clean into one call with `fail_fast` + `summary_only` + per-section summaries. Two problems decided it: (1) **its check set did not match the real gate** — `ci_pipeline_local` advertised "CI critical checks" while running none of the `pre-commit` hooks that this repo actually enforces (lizard CCN, fn-param/nloc ratchets, docs link check, typos, crate dep policy), so a green run read as "CI passed" while the most common hook rejections were invisible; (2) `ci_pipeline_local` and `quality_workspace` were the **same parameter surface** with different defaults (`run_fmt` / `run_cargo_fmt_check`, `run_ruff_check` / `run_ruff_check`, …), leaving the model to pick between two indistinguishable tools. - **`structured_patch` now commits through the shared write pipeline (optional CAS + atomic replace) and previews a unified diff**: it was the only **structured-data** write tool that rewrote a whole file with a bare `fs::write` — no revision check, no temp file, and a preview that reported `新文件大小: N 字节` instead of what would change. (`apply_patch` still writes with a bare `fs::write` too, but it is a patch-application tool with its own root-checked path resolution and typed errors; its gaps — no `dry_run`, no atomic replace — are separate work, not conflated here.) It now calls `file::write_bytes_with_revision_guard` (the same entry `modify_file`'s `full` mode uses): same-directory temp → inherit owner/permissions/xattrs → `fsync` → revision check → `rename`, so a concurrent reader never sees a truncated file and a `nlink > 1` target keeps its inode. New optional **`base_revision`** provides the CAS: pass the `revision` from a `read_file` output header and a stale file yields `错误[stale_revision]` with nothing written. It is deliberately **not** auto-bound to the turn's `read_file` (unlike line-mode edits) — key-path edits do not drift the way line numbers do, so requiring a baseline would break existing callers for no safety gain. Previews (`dry_run` omitted or `true`) now return the unified diff (`--- a/<path>` / `+++ b/<path>`, rendered by the same `text_diff::diff_unified` and byte-budgeted) instead of a byte count, and they honour an explicit `base_revision` too — a stale snapshot fails the preview rather than handing back a diff that looks safe. The diff is only built on the preview path, so a write does not pay for rendering it. Note the write still re-serializes the whole document (JSON → pretty, TOML/YAML regenerated without comments), which is why a previewed diff often looks like a full re-layout; that is now called out in `docs/工具说明.md` together with the advice to prefer `modify_file` / `search_replace` for comment-bearing configs. The write path also propagates the typed `错误[...]` codes on its first line instead of wrapping them as `写入失败: {e}`. Pinned by four tests in `structured_data_patch/tests_revision.rs`. See `docs/工具说明.md`.

- **`modify_file` guards collapsed into one `guard` object, and its description shrank ~4×**: the four flat guard parameters (`expect_content` / `expect_first_line` / `expect_last_line` / `expect_line_content`) were defined **twice** — once on `ModifyFileArgs`, once again inside `ModifyFileEditArgs` — with eight duplicated doc blocks and the mutual-exclusion rules restated in prose at each site. The `modify_file` description dropped from **1620** to **598** characters by leaving the exclusion matrix, the error-code list and the mode table to `docs/工具说明.md`: it is resent on every turn, and it alone accounted for 20% of the whole `file_core` spec file. New `file::write_guard` unit tests pin the precedence (guard beats legacy) and the legacy fallback. See `docs/工具说明.md`.

- **Preview no longer requires a revision baseline, and `append_file` joined the single write knob**: a preview writes nothing, so gating it behind `missing_revision_baseline` / `stale_revision` only punished the safe path — with `dry_run` defaulting to `true`, "just show me the diff" became "refused to write" for any line-mode call that had not `read_file`'d the target this turn, and the error text (「拒绝写入」) described an operation nobody asked for. `modify_file_try` now resolves `dry_run` once, before dispatch, and skips only the *turn-binding* baseline check for previews (an explicit `base_revision` still always validates, and the write path still verifies right before the rename). Preview tests that had been forced to pass `allow_stale_revision=true` dropped it, and `test_write_tools_default_to_preview_without_dry_run` now pins "preview works with no baseline". **`append_file` was the last write tool outside the knob** (`#[serde(default)]`, so it wrote when `dry_run` was omitted) — the one direction where the new mental model was unsafe: a caller who learned "omit `dry_run` → preview" would have silently written. It now defaults to `true` too, so all four write tools share one rule. The four scattered `dry_run` reads collapsed into `write_ops::dry_run_arg`, so a new dispatch branch cannot re-introduce an old default. `SearchReplaceArgs.confirm` / `StructuredPatchArgs.confirm` are marked deprecated in their schema doc. See `docs/工具说明.md`.

- **`modify_file` now defaults to preview (`dry_run=true`), and the three write tools share one write gate** — breaking for callers that relied on "omit `dry_run` and it writes". The old state had **two** separate inconsistencies: `modify_file` defaulted `dry_run=false` (wrote unless told otherwise) while `search_replace` / `structured_patch` defaulted `true`; and those two additionally demanded `confirm=true` on top of `dry_run=false`, a second lock that the model always supplied anyway — its only reliable effect was producing "silently didn't write" when forgotten (it happened to me mid-session). Now there is one rule: **omit `dry_run` and you get a preview; pass `dry_run=false` and it writes.** `confirm` is no longer checked by `search_replace` / `structured_patch` (fields kept so existing calls stay valid). Still deliberately kept: `delete_files` / `delete_dir`'s `confirm` (destructive) and `modify_file`'s `confirm_full_overwrite` (high-risk shrink). **Migration**: add `"dry_run":false` to any `modify_file` call that expects a write — 47 test call sites and 4 default-value read sites updated here. It now returns **`错误[missing_revision_baseline]`** and refuses to write (`NOT_WRITTEN_HINT`), naming three ways forward: `read_file` first, pass the `revision` it returns as `base_revision`, or opt out explicitly with `allow_stale_revision=true`. ### Removed

- **Four more tools removed: `run_lints`, `hash_file`, `chmod_file` and `text_transform`**: each had a command-line or in-process substitute the model can reach directly, and none carried a semantic the replacement lacks — but every removal trades a little convenience for one fewer name in the registry, so the costs are named explicitly. **`run_lints`** aggregated `cargo check` + `cargo clippy` + `npm run lint` + `ruff check` into one call; with it go `lint.rs`, `frontend_tools.rs` (its only remaining consumers were `run_lints`), `python_tools::ruff_check` / `parse_rel_paths` (same reason), `RunLintsArgs` and the whole `specs/format_lint.inc.rs` shard. Cost: a combined lint check is now **three or four `run_command` round-trips** instead of one, and the "no `Cargo.toml` / no `package.json` → skip" guards are gone. **`hash_file`** streamed SHA-256 / SHA-512 with an optional `max_bytes` prefix; `sha256sum` / `sha512sum` are now allowlisted, so the prefix form is `sha256sum f | cut -c1-16` and the whole-file form is the plain command. Cost: no `digest_hex:` field, no streaming buffer cap, and very large files hit `run_command`'s output cap. **`chmod_file`** wrapped `set_permissions` behind `confirm=true`; `chmod` is allowlisted. Cost: the `confirm` gate and the octal-mode validation are gone — a malformed mode now fails inside `chmod` rather than before it. **`text_transform`** did Base64 / URL encode-decode / short hash / line join-split in memory; `base64` is now allowlisted, `sha256sum` + `cut` covers the short hash, `tr` / `paste` cover join-split, and URL encode-decode goes through `python3 -c`. **That last one is the largest convenience loss of the four**: percent-encoding has no small CLI equivalent, and it is exactly the kind of transform a model performs *unreliably* by hand — expect more `python_snippet_run` use here. Legacy-ratchet baseline **29 → 28** (26 → 25 without `archive-tools`); Typed tools 44 → 41. **Breaking**: `allowed_tools`, role lists and workflow nodes pinning any of the four must switch to `run_command` (`sha256sum` / `sha512sum` / `chmod` / `base64` allowlisted; URL encoding via `python3`). Removed alongside: the three `hash_file_*` error codes, `HashFileAlgorithm` / `HashFileArgs` / `ChmodFileArgs` / `TextTransformOp` / `TextTransformHashAlgo` / `TextTransformArgs`, both summary bindings, all `dev_tag` mappings, `chmod_file` in `registry_policy`'s write-effect list and `hash_file` / `chmod_file` in `codebase_semantic_invalidation`'s path-arg list. The `orch_single_agent_tool` e2e scenario — whose prompt told the model to call `text_transform` — was **retargeted at `json_format`** rather than deleted, because it exists to prove the tool-call → final-answer loop, not that specific tool. See `docs/工具说明.md` / `docs/en/TOOLS.md`.

- **`rust_compiler_json` removed: its JSON output duplicated `cargo_check`**: the tool ran `cargo check --message-format=json`, filtered `reason == "compiler-message"` lines and re-rendered each as `[error] E0308 mismatched types` + `message.rendered` + the first 5 spans + the first 8 children. Every one of those pieces is something cargo already prints — `rendered` *is* cargo's human-readable block (arrow, snippet, labels) and the extra span / child lists restate it — so the net value over the existing typed, read-only `cargo_check` was only "number the diagnostics and cap them at `max_diagnostics`". Deleted: the `ToolSpec`, the `cwd_maxlen` runner entry, `RustCompilerJsonArgs`, the `dev_tag` tag, the `builtin_parallel_sync_denied_exact` entry (it was already excluded from the parallel read-only batch, precisely because it shells out to cargo), and the whole `cargo / rustc JSON` section of `rust_ide.rs` (~230 lines incl. `parse_cargo_check_args` / `build_cargo_check_command` / `collect_compiler_messages` / `format_compiler_message` and its smoke test). Legacy-ratchet baseline **33 → 32** (30 → 29 without `archive-tools`). **No read-only capability is lost** — unlike a downgrade to `run_command`, the replacement `cargo_check` is itself read-only, so the read-only retry, `Ask`·`Plan` gating and TTL cache still apply. **Breaking**: anything pinning the name in `allowed_tools`, roles or workflows must switch to `cargo_check` (raw JSON: `run_command` + `jq`).

- **`changelog_draft` / `license_notice` tools removed, taking the `release_docs` module with them**: both were release-time conveniences with strong command-line substitutes, and each carried a legacy `String` runner whose failures `parse_legacy_output` had to infer from text. `changelog_draft` (`git log` → Markdown draft, grouped by date / `flat` / `tag_ranges`) is covered by `gh_release_create`'s `auto_notes` (the same "recent tag → HEAD commit list" draft) and by `git` / `run_command` with `git log --pretty`; `license_notice` (`cargo metadata` → `crate → license` table) is covered for *gating* by `cargo deny check licenses` (already wired in `deny.toml` and CI) and, for the table itself, by `run_command` + `cargo metadata --format-version 1 | jq` — a multi-round-trip answer instead of one tool call, which is the deliberate trade being made. - **`format_files` tool removed** — its `.rs` branch was broken: it shelled out to `rustfmt` **without `--edition`**, and standalone rustfmt does not read `Cargo.toml` (that is `cargo fmt`'s job), so it parsed every file as **edition 2015** and failed on any edition-2018+ syntax. On this repo (`edition = "2024"`) that meant `format_files` answered `rustfmt 格式化失败，退出码：1` + `error: let chains are only allowed in Rust 2024 or later` for files such as `src/cm_tools/tools/format.rs`, **even though `cargo fmt --check` was clean** — the same wrapper worked on 2015-only files and failed on newer ones, which read like the file itself was broken. ### Fixed

- **The `search_replace` tool-card line now spells the tool the way the registry does**: `SearchReplaceSummaryArgs::summary_line` hard-coded `search-replace{}: …`, while the tool itself is `search_replace` — so every client showed a hyphenated name the tool list never uses (`search_replace (preview): a.rs / "foo"`; previously `search-replace (preview): …`). No other summary line spells a tool name with a hyphen: the rest either use plain words (`read file:` / `delete directory:` / `chmod:`) or the registry name itself (`terminal_session exec …` / `gh api …`), so this was a typo rather than a convention. No protocol change — the field, its type and its semantics are untouched, and the client TUI's `-`/`_` normaliser simply becomes a no-op: it can be deleted on its own schedule, with no behaviour change either way (nothing in this repo keys on the hyphenated form), so no Client-repo change is required to ship this. Pinned by tests in `cm_tools::tools::tests` covering both the preview and the write form.

- **`run_command` tool-card summary no longer degrades to the placeholder for array-shaped commands**: `RunCommandSummaryArgs.command` was declared `String`, so a model that wrote the whole command as an array (`{"command":["git","status","-sb"]}`) made the struct fail to deserialize — the summary fell back to `tool: run_command`, and every client then had to re-parse the argument JSON to recover the command (the Web shell and the TUI each carried their own copy of that recovery, which is exactly how the two drifted apart). `command` is now a `serde_json::Value`: a string stays verbatim (it *is* the line to display, so quoting it would be wrong), an array becomes one token per element, and `args` is appended in both shapes — `{"command":["git"],"args":["status","-sb"]}` renders `git status -sb` as well. An empty command still yields `None`, leaving the placeholder decision and any last-resort rendering to the client (unchanged). Pinned by three tests in `cm_tools::tools::tests` (array command, array plus `args`, empty command).

- **Spurious `run_command` failures on multi-line invocations**: the tool echoes the raw argv after `命令：`, so a multi-line argument (`git commit -m "…" -m "…"`) makes that echo span dozens of lines. `strip_leading_command_invocation_line` drops only up to the first newline, so the "first line" used for status was really **message body**: `parse_exit_code` missed `退出码：0`, the parser fell back to the `失败` / `超时` keyword heuristic, and reported `ok=false` with `exit_code=null` **even though the command had exited 0** (seen on `git commit` whose body contained 「失败」). The exit code is now also read by scanning the header region up to the first `标准输出：` / `标准错误：` marker, so multi-line echoes still yield the real code; the scan only trusts outputs carrying those markers, so an `退出码：N` inside another tool's payload (e.g. a file returned by `read_file`) is never mistaken for status. Non-zero exits still fail. The parser moved to `cm_tools::tool_result::run_command` — `tool_result/mod.rs` had been sitting exactly at the 920-line cap, so any further edit there was blocked.

### Security

- **`AGENTS.md` symlink escape blocked**: that file's content is injected into `system` and sent to the model, so a workspace symlink pointing at an arbitrary local file (e.g. `/etc/passwd`) would have pulled it into the conversation. The loader now canonicalizes the path and **ignores** the file when it resolves outside the workspace root; symlinks pointing inside the workspace still work. Unix-only. See `docs/配置说明.md`.

- **Cleared the three RustSec vulnerabilities flagged by `cargo audit`**: bumped three transitive TLS crates to their fixed patch releases — **`rustls-webpki`** `0.103.15` → `0.103.16` (**RUSTSEC-2026-0382**, certificate verification may accept distrusted intermediates), **`webpki-roots`** `1.0.6` → `1.0.10` (**RUSTSEC-2026-0381**) and **`webpki-root-certs`** `1.0.6` → `1.0.10` (**RUSTSEC-2026-0383**) — the latter two because their bundled root sets still trusted distrusted emSign intermediates. All three live in the existing `rustls 0.23` graph, so this is a lockfile-only patch-level bump: no source, wire-protocol or config change. The five remaining `cargo audit` entries are upstream-blocked **`unmaintained`** warnings (`paste`, `term_size`, `zbus_names`, `zvariant`, `zvariant_derive`), which `cargo audit` reports as non-fatal and which stay documented as transitive.

**crates.io** release of the single crate **`crabmate`** (default feature **`server`**; Client pins **`protocol`**). Install: **`cargo install crabmate`**. Git tag **`v0.7.0`** matches this package. SSE wire protocol stays **v2**. Cut as a **minor** per [`docs/design/client_contract_versioning.md`](docs/design/client_contract_versioning.md) §2.2 (at **`0.y.z`** a minor may denote a breaking change): this release is dominated by **tool-surface consolidation** — dozens of thin CLI wrappers are removed and replaced by generic **`run_command`** (the default allowlist is expanded accordingly), so read the **BREAKING** entries below before upgrading. Additive highlights: **`serve --yes`**, background-job monitoring tools, **`GET /tools/plugins/{file}`**, context-archive retention keys, and **`GET /conversation/messages?include_archive=true`**.

### Added

- **`serve --yes` to bypass the command allowlist**: a new `serve` flag replaces `allowed_commands` with the allow-all sentinel **`["*"]`**, so **`run_command`** (and `terminal_session` first-frame `exec`) no longer validates the command name and runs any program. The sentinel is honored at the single host-side gate (`resolve_run_command_exec_path`), the approval layer (`cmd_missing_from_allowlist`, shell-wrap approval), and the peripheral consumers (`gh_allowed`, `error_output_playbook`, plugin/dynamic-tool validation, `doctor`), and is preserved across `POST /config/reload`. It is equivalent to **`CM_ALLOWED_COMMANDS=*`** and is intended **only** for fully trusted or already-isolated (container / dedicated host) environments; it does **not** disable workspace-external path approval or argument-safety checks. See `docs/命令行与路由.md` / `docs/工具说明.md` / `docs/配置说明.md`.

- **Background-job monitoring tools**: added two model-facing tools for the background tool-job lifecycle (design doc `docs/design/background_tool_jobs_contract.md` §9). **`background_job_output`** (read-only) incrementally pulls a job's output (`tail -f` semantics) via `tool_job_id` + optional `cursor` (the previous `next_cursor`), returning stdout/stderr deltas plus `next_cursor` and `eof`; it reuses the existing `ToolJobRegistry::poll_output` and is exempt from the same-turn read-only dedup cache (its output changes within a turn). **`background_job_cancel`** cancels a job (`queued` → `cancelled`, `running` sets the cancel flag, already-`cancelled` is idempotent success, other terminal states cannot be cancelled); it reuses `ToolJobRegistry::cancel`, is **termination** (not execution launch) so it does not violate the ADR's "no new execution-launching tool group" constraint, and is registered in `write_effect_tools` for auditing. Both are injected through `ToolJobsToolHost` (no allowlist approval). See `docs/工具说明.md` / `docs/en/TOOLS.md`.

- **`GET /tools/plugins/{file}` endpoint**: read-only single-file detail for a workspace dynamic tool definition (`<workspace>/plugins/{file}`), returning `file` / `name` / `description` / `valid` / `error` / `command_allowed` / `parameters` / `args` / `pass_args_json`. `{file}` must match `[A-Za-z0-9_-]+.json` (otherwise **400** `INVALID_PLUGIN_DEFINITION`); an unset workspace or a missing file returns **404** `PLUGIN_NOT_FOUND`. Closes the read-only tail of the tool-management API (design doc `docs/design/tool_management_api.md` §3.4). See `docs/命令行契约.md` / `docs/命令行与路由.md`.

- **Context-archive retention configuration**: two new `[agent]` keys make the cross-turn original-text archive (design doc `docs/design/context_window_compaction.md` §3.8 / §4.2) tunable. **`context_archive_max_rows_per_conversation`** (`CM_CONTEXT_ARCHIVE_MAX_ROWS_PER_CONVERSATION`, default **`256`**, `0` = unbounded) caps the per-conversation archived-prefix rows and drives the SQLite `prune` cascade; reclaiming an old prefix makes branch points older than the retained window fail to re-expand (the branch API returns an explicit error). **`context_archive_codec_min_bytes`** (`CM_CONTEXT_ARCHIVE_CODEC_MIN_BYTES`, default **`4096`**) is the archive-body codec threshold (below it `identity`, otherwise `gzip`). Both are hot-reloadable and validated (`0..=10_000_000` / `0..=4_194_304`). See `docs/配置说明.md` §会话持久与保留策略.

- **`/btw` LLM-summary toggle**: one new `[agent]` key, **`context_btw_summary_enabled`** (`CM_CONTEXT_BTW_SUMMARY_ENABLED`, default **`false`**), gates whether the off-the-record **`/btw`** side-question path (design doc `docs/design/context_window_compaction.md` §3.10 / §5.3.6) may make **one** optional LLM summary attempt while doing its read-only dry-run compaction. It is **off by default** so the default btw path stays purely local (no extra model call, no cost/latency); when enabled it follows the **same** summary-trigger rules as the main turn but still **never** persists (`/btw` never writes canonical, archive, or artifacts regardless). Hot-reloadable; the summary-only-optional behavior is also asserted by the regression `btw_readonly_summary_flag_defaults_off`. See `docs/配置说明.md` / `docs/en/CONFIGURATION.md`.

- **`GET /conversation/messages` can now include the archived original text**: a new optional query parameter **`include_archive`** (boolean, default **`false`**) makes the response carry an additional optional **`archive`** array with the conversation's already-archived (moved-out-of-canonical) original messages when set to `true` (design doc `docs/design/context_window_compaction.md` §5.3.4 C2). The field is omitted when empty (`skip_serializing_if`), so the default response body is byte-for-byte the same as before and old Clients are unaffected. Only the SQLite backend persists an archive (the memory backend returns an empty `archive`); `archive` rows share the same `WebClientSnapshotMessage` shape as `messages`. The OpenAPI snapshot (`docs/openapi.json`) and `docs/命令行与路由.md` are updated.

### Changed

- **Cancelled turns now persist their produced content**: when a Web stream turn is stopped (**`POST /chat/stream/{job_id}/cancel`**, or the SSE receiver drops while a cooperative cancel is pending — `cancelled_by_signal`), the partial output already produced in that turn (assistant text, `tool_calls`, completed `tool` results) is now **best-effort persisted** to the conversation store instead of being discarded, so the **next** turn's model context includes "what I already produced before the user interrupted". Two previously-leaking branches are covered: the `Ok` path (the agent had already merged the partial assistant and committed the derived view, but `stream_job_outcome_after_agent_turn` did `let _ = commit`) and the `Err`/`UserCancelled` path (the failed turn never wrote back). The interrupted path writes back **append-only** — no compaction, no archive, no `ConversationTurnGroup` derived view (`ModelContextView::append_current_turn_to`) — and completes a half-finished tool batch (`assistant(tool_calls=[A,B]) + tool(A)`) with placeholder `tool` messages so the persisted sequence stays legal (otherwise the next request would be rejected with an upstream **400**). Persistence reuses the existing CAS (`save_conversation_messages_if_revision`; `Conflict` is logged only), is skipped when the turn produced no visible assistant output, and **does not** change the SSE terminal semantics — the cancel path still emits only **`STREAM_CANCELLED`** with no `conversation_saved` / state snapshot / `stream_draining` and no long-term-memory async indexing. See `docs/SSE协议.md` / `docs/en/SSE_PROTOCOL.md` / `docs/design/context_window_compaction.md`.

- **Persist-time injection stripping now also drops execution-constraint ephemeral system messages**: the pre-persist / pre-structural-commit sanitize chain (design doc `docs/design/context_window_compaction.md` §3.7.1) is extracted into a single named helper **`strip_persist_injections`** (`src/chat_job_queue/stream_finish.rs`) and gains a fourth step — `retain(!is_execution_constraint_ephemeral_system)` — so any execution-constraint **system** injection that survives `outer_loop`'s per-turn `retain` is now **explicitly** removed before persistence instead of relying on that implicit side effect. **Behavior change**: previously such residue would have been persisted into `canonical`; the chain still **keeps** the baseline summary (`CRABMATE_CONTEXT_SUMMARY_NAME`) and the first-turn workspace profile (`CRABMATE_FIRST_TURN_WORKSPACE_CONTEXT_NAME`).
- **Raised the embedded default output/context budget for the shipped DeepSeek default**: `config/default_config.toml` now ships **`max_tokens = 16384`** (was **4096**) and **`llm_context_tokens = 262144`** (was **65536**, i.e. 256k), matching the real `deepseek-v4-flash` gateway (≈1M-token window, 384k max output, thinking on by default) instead of the old conservative "64k" placeholder. The higher completion cap reduces `finish_reason=length` truncation (reasoning tokens count toward the completion budget); the larger window stops the final-request token budgeter from over-trimming input, while `reserved_output_tokens = min(max_tokens, window - 256)` still keeps requests from exceeding the window. Both keys stay within their validated ranges (256–32768 / 0–10,000,000) and remain overridable via `config.toml` / `CM_MAX_TOKENS` / `CM_LLM_CONTEXT_TOKENS`. See `docs/配置说明.md` §上下文窗口.

- **Outer-loop recovery for truncated turns that also call tools**: when a turn is flagged truncated (upstream `finish_reason == "length"`, or the stream is cut off before `[DONE]`) **and** the same model response also carries `tool_calls`, the turn takes the `ProceedToExecuteTools` path and previously skipped the stop-turn continuation nudge. The outer loop now injects the same bounded continuation feedback **after the tools run** (still ≤2 per turn, shared with the stop-turn path) and forces the next iteration, so such turns resume instead of stalling as if complete. Pairs with the `stream_ended.reason="truncated"` terminal state; `SSE_PROTOCOL_VERSION` is unchanged (additive soft value). See `docs/design/run_loop_state_ownership.md` / `docs/design/client_contract_versioning.md`.

- **Background jobs now enabled by default**: **`[tool_registry] background_jobs_enabled`** (`config/tools.toml`) now defaults to **`true`** (was **`false`**), so **`run_command`** (and any tool in **`background_job_async_tools`**) can be launched with **`async: true`** out of the box. The model must still pass **`async: true`** explicitly — synchronous behavior is unchanged — and the async path still **rejects interactive approval** (the command must already be allowlisted or `AllowAlways`), so this does not widen the approval surface. The default **`background_job_async_tools`** stays **`["run_command"]`**. See `docs/design/background_tool_jobs_contract.md` §6 / `docs/配置说明.md`.

### Fixed
- **A cancelled turn can no longer poison the next request with an incomplete `tool_calls` batch**: when a Web stream turn is stopped while the model is still streaming a tool call, the persisted history could end with `assistant(tool_calls=…)` whose `arguments` were truncated and which had no `tool` response. Every later turn then failed upstream with **400** (`An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'`), so the conversation appeared to ignore "continue". Two layers now prevent it: (1) the cancel persistence path (`save_cancelled_turn_best_effort`) runs the same repair as the `Err`/`UserCancelled` path before writing — dropping calls that were never executed and whose `arguments` are not valid JSON, then filling placeholder `tool` messages for any remaining unanswered calls; (2) outbound request assembly (`conversation_messages_to_vendor_body` / `normalize_stripped_messages_for_vendor_body`) self-heals **existing** dirty histories by inserting the missing `tool` messages (logged as a warning), so already-affected conversations recover without manual database edits. Calls that do have a `tool` response keep their call/response pairing and their invalid `arguments` are still normalized to `{}` by the existing sanitizer.

### Added

- **`docs/openapi.json` snapshot**: committed OpenAPI 3.0.3 snapshot of `build_openapi_spec()` with a lock-step unit test (`openapi_docs_snapshot_matches_spec`); regenerate after route/contract changes or version bumps via `CRABMATE_BLESS=1 cargo test --lib web::openapi::tests::openapi_docs_snapshot_matches_spec` — same maintenance model as `man/crabmate.1`. Deleting mid-turn is safe: the in-flight turn's next save hits the existing optimistic-concurrency path and fails with **`CONVERSATION_CONFLICT`** instead of resurrecting the row. The Client sidebar index is *not* cascaded — Clients keep maintaining their own `sessions` rows. Works for both backends (memory and SQLite) and is documented in `docs/openapi.json`, `docs/命令行与路由.md` / `docs/en/CLI.md`, and `docs/design/conversation_management_api.md`.

Applies to both the memory and SQLite backends; pruning runs after each successful save and from an hourly background task (plus once at `serve` startup), so an idle SQLite process no longer accumulates rows forever. Both keys are **hot-reloadable** via `POST /config/reload`; lowering the cap does not delete existing rows on the spot but takes effect on the next save / prune. See `docs/配置说明.md` / `docs/en/CONFIGURATION.md`.
- **`/btw` side-question built-in command**: `POST /chat` and `POST /chat/stream` now recognize **`/btw <问题>`** — a short-circuited *off-the-record* side question that answers **with the current conversation context but is never persisted** (the Q&A neither lands in `conversations.db` nor grows the session context) and is sent to the model with **no tools** (`tools: []` / `tool_choice: "none"`). - GitHub Actions **Release** workflow (`.github/workflows/release.yml`): tag `vX.Y.Z` (or `vX.Y.Z-rc.N`) → `make package` + GitHub Release with tar.gz/deb; notes from this file’s core `X.Y.Z` section; re-run updates the same Release.
- Default English [`README.md`](README.md) with Chinese companion [`README.zh.md`](README.zh.md).

### Changed

- Path A: removed in-repo `frontend/`, desktop/mobile shells, and Playwright ownership from this repo; document pointers target Client.
- CI package job: server-only artifacts; test job avoids full `cargo clean` (clears incremental only when free disk is low).
- Packaged unit uses `--config /etc/crabmate/config.toml` (prompt path anchor); does **not** force `--no-web` so `CM_WEB_STATIC_DIR` can mount a Client-built UI.

### Fixed

- `crabmate-gen-man` packaging requires `--features gen-man`.
- Deb package smoke grep paths aligned with `dpkg-deb -c` output (`./usr/bin/…`).

### Known limitations (0.1.0)

- **Trusted workspace** model: `run_command` allowlist includes powerful tools (`bash`, `git`, `cargo`, …). Not a multi-tenant SaaS.
- Chat job queue is **single-process**; no Redis/SQS horizontal scale yet.
- Process auth is shared **Bearer** (optional); no per-user accounts in-process (use a gateway/BFF if needed).
- Default Cargo features include **`mcp`** (with `web`); in-process **`repl`/`tui` features removed** (D2.2). Heavy options such as **`fastembed`** remain opt-in.
- Systemd service user has a **minimal `PATH`**; extend via `/etc/crabmate/crabmate.env` for host toolchains. Bypass HTTP proxies for `127.0.0.1` when probing locally.
- Compatibility-layer shrink items **B2–B4**, full unwrap audits, and agent benchmarks remain backlog ([`docs/待办清单.md`](docs/待办清单.md)).
