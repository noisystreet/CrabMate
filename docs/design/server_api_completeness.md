# ADR：Server API 完备度边界与演进基线

> **状态**：Proposed（2026-08-25）  
> **范围**：`crabmate serve` 暴露的 HTTP/SSE API、官方 Client 消费契约与第三方集成边界。  
> **契约真源**：运行时路由与 [`GET /openapi.json`](../命令行与路由.md)；SSE 行级语义见
> [`docs/SSE协议.md`](../SSE协议.md)。

## 1. Context

CrabMate Server 同时面对两类消费者：

1. 官方 Web、Desktop 与 `crabmate-tui`，通过 HTTP/SSE 完成对话、审批、会话恢复、工作区操作和设置管理；
2. 脚本、IM bridge 或其它第三方系统，通过同步 JSON、异步任务、Webhook 或 SSE 集成 Agent。

两类消费者对“完备”的要求不同。官方 Client 需要单用户产品闭环和双端契约一致；通用平台 API
还要求幂等、限流、租户隔离、持久任务、多副本恢复和更完整的 SDK/示例。若不区分这两个目标，
容易把“官方 Client 已可用”误写成“公网多租户平台已经就绪”。

当前接口已经覆盖：

- 同步、异步和 SSE 流式对话；
- 工具审批、流取消、后台工具任务轮询与取消；
- 会话历史、分页、revision 与分叉；
- 工作区、文件、上传、Skills、配置和用户数据；
- GitHub Device Flow、仓库上下文与 PR checks；
- `/health`、`/status`、统一错误体、`x-request-id` 和 OpenAPI 3.0。

路由与 OpenAPI 的 path/method 对齐已有自动测试；SSE 使用独立协议版本、金样和 Client 解析门禁。
但异步任务与流恢复状态仍以单进程内存为主，认证仍是可选的单一共享 Bearer，且没有 HTTP
幂等键、内建配额或账号级租户模型。

## 2. Decision

### 2.1 产品边界

采纳以下边界：

- Server API 的首要目标是成为**官方 Client 的稳定单用户/单工作区后端契约**。
- 第三方同步、异步、Webhook 与 SSE 集成属于**支持能力**，但在下述平台级门槛完成前，
  不宣称为多租户、高可用或可水平扩展的通用 Agent 平台 API。
- 用户账号、组织、计费等身份系统默认放在 API 网关或 BFF；若未来要进入 Server 进程，
  必须另开安全与数据隔离 ADR。
- OpenAPI 负责 HTTP path、method、请求/响应 schema 与鉴权摘要；
  `docs/SSE协议.md` 继续负责 SSE 帧和控制面语义，不尝试把行级协议伪装成普通 JSON 响应。

### 2.2 当前完备度结论

| 维度 | 当前结论 | 主要依据 |
|------|----------|----------|
| 官方 Client 功能闭环 | **基本完备** | 对话流、审批、会话、工作区、上传、设置、GitHub 与 MCP 已有服务端入口和 Client 消费 |
| HTTP 契约治理 | **基本完备** | OpenAPI 3.0、统一 `ApiError`、稳定错误码、`x-request-id`、路由对齐测试 |
| SSE 契约治理 | **完备度较高** | 独立协议版本、能力握手、重连语义、金样与双端解析门禁 |
| 第三方单实例集成 | **可用但有约束** | 同步、异步、Webhook、SSE 均可用；审批场景必须使用 SSE |
| 多副本可靠性 | **不完备** | async job 与 SSE resume 依赖进程内状态；重启或跨实例可能失效 |
| 安全与租户 | **不完备** | 单一共享 Bearer；未提供账号、租户、每 Key 配额与轮换窗口 |
| 幂等与流量治理 | **不完备** | 无 `Idempotency-Key`、按 Key/IP/conversation 的限流或计费配额 |
| 运维生命周期 | **部分完备** | 有健康、状态和请求关联；上传配额/清理及任务持久化仍缺失 |
| 端到端 API 回归 | **部分完备** | 路由/OpenAPI 与协议金样较强，非真实 LLM 的 handler 矩阵仍偏少 |
| 第三方开发体验 | **部分完备** | 有 OpenAPI 和集成说明，缺官方 curl/Python SSE 最小示例与稳定 SDK |

因此当前可表述为：

- **官方 Client 后端：基本完备，可作为正式产品主路径。**
- **第三方单实例集成：可用，集成方必须消化文档中的审批、重连和鉴权约束。**
- **公网多租户平台：尚未达到完备标准。**

不把主观分数作为发布门槛；是否“完备”由下一节的能力门槛判断。

### 2.3 平台级完备门槛

只有同时满足以下条件，才能把 Server API 定位升级为通用平台 API：

1. **重试安全**：对会产生模型调用或外部副作用的入口提供幂等键或明确的业务去重机制。
2. **持久任务**：async job、Webhook 投递状态和必要的流恢复元数据可跨进程恢复。
3. **多副本语义**：无需依赖未声明的会话粘性，或在部署契约中明确并自动校验粘性要求。
4. **身份与隔离**：至少具备多服务级 Key、轮换窗口、租户归属和资源访问隔离。
5. **限流与配额**：按 Key、IP 或 conversation 执行有界限制，并给出稳定的超限错误码与重试语义。
6. **资源生命周期**：上传、任务结果、会话和审计数据有大小上限、TTL、清理与容量告警。
7. **可验证契约**：关键 handler 的成功、鉴权、校验、冲突、取消和恢复路径有自动化回归测试。
8. **集成材料**：提供可运行的同步、异步/Webhook、SSE+审批示例，并说明版本与兼容窗口。

### 2.4 演进优先级

按风险与收益排序：

1. `Idempotency-Key` / 业务消息 ID 去重；
2. chat async 与流任务的持久化及多副本语义；
3. 限流、配额、多 Key 与轮换；
4. 上传和任务结果的配额、TTL 与清理；
5. handler 级契约测试矩阵；
6. 第三方最小示例与 SDK 生成说明；
7. 是否引入 URL API 主版本，留到出现第一个不可兼容 HTTP 变更时另行决策。

## 3. Consequences

### 正面影响

- 官方 Client 不必等待平台化能力即可继续稳定演进。
- 文档和发布说明能够准确区分“产品主路径可用”与“平台级能力完备”。
- 后续 API 投资有可检查的门槛，不再用路由数量代替可靠性、安全性和可运维性。
- OpenAPI 与 SSE 文档继续各自承担适合的契约职责，避免重复真源。

### 代价与约束

- 第三方集成在现阶段需要自行处理幂等、租户、配额和部分故障恢复。
- 多副本部署仍需单实例承接或会话粘性，直到任务状态外置。
- Server 与 Client 的协议变更继续要求双仓同步验证。
- 本 ADR 只定义边界和门槛，不替代各能力的字段级 API 设计、迁移方案和安全评审。

## 4. Alternatives Considered

### 4.1 以“现有路由都能调用”认定 API 已完备

不采纳。路由覆盖不能证明重试安全、多副本恢复、租户隔离、容量治理和兼容策略已经完成。

### 4.2 在 Server 内立即建设完整账号与多租户平台

不采纳。当前官方 Client 以单用户 Server 为主，直接引入账号、组织和计费模型会显著扩大数据迁移、
授权和运维成本。短期由网关/BFF 承担身份层更符合现有产品边界。

### 4.3 只保留 SSE，对外删除同步与异步接口

不采纳。SSE 适合交互式审批和增量展示；同步 JSON 与异步/Webhook 对脚本和 IM bridge 仍有独立价值。
三种入口应共享核心执行与错误契约，而不是强迫所有消费者实现同一种传输。

### 4.4 把 SSE 所有控制帧完整编码进 OpenAPI

不采纳。OpenAPI 3.0 对流内多形态事件的表达有限；保持 HTTP 握手在 OpenAPI、行级协议在独立版本文档
和金样中，更容易验证且不制造重复真源。

## 5. Review Triggers

出现以下任一情况时复核本 ADR：

- Server 引入多枚 API Key、账号或租户模型；
- async/chat job 状态迁移到 Redis、数据库或外部队列；
- 部署目标从单实例转为默认多副本；
- HTTP 出现第一个需要不兼容迁移的字段或语义；
- 官方 Client 不再是 Server API 的首要消费者；
- 上述平台级完备门槛全部满足，需要调整产品定位。
